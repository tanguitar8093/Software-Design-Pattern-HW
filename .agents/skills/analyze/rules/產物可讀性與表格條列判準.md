# Rule 1 - 表格內多值必須條列，禁止擠成一行

- Level: `MUST`
- 規格覆蓋矩陣與驗收覆蓋矩陣的多值欄（實際介面、切片、任務）必須條列，不可只用空白或分號把多個 ID 糊成一行。
- Markdown 表格列不能直接換行寫 `-` 時，格子內可用 HTML 清單，或編輯器可預覽的格子內條列。
- 任務欄只寫該切片的 RGR 區間（例如 `T005–T007`），不把整個 package 的任務編號一次列出。

## Good Example

- 這個例子是好的，因為一個格子裡看得出多個切片。

```html
<ul>
<li><code>BE-API-001A</code></li>
<li><code>FE-E2E-001A</code></li>
</ul>
```

## Bad Example

- 這個例子是壞的，因為多個 ID 擠在同一行。

```md
| FR-001 | … | BE-API-001A BE-API-001C FE-E2E-001A FE-E2E-001C | T005–T007 T011–T013 T017–T019 T023–T025 |
```

# Rule 2 - 下一步建議必須是可執行清單

- Level: `MUST`
- 報告的「下一步建議」必須用編號或 `-` 條列，不可寫成一段散文。
- 無可修項時，第一條必須寫「無可修項」，並寫明不阻擋進入 `/implement`。排除（不委派）項另列，不得混進要執行的 skill 清單。
- 有可修項時，每條必須寫：skill、範圍（檔或 ID）、做什麼。順序必須上游先於下游，最後一條可修路徑是再跑 `/analyze`。
- 不得把「人手動改來源檔」或「請自行檢查」寫進下一步。
- 不得建議修改已列入排除的上游活包 Mock／`tests/run.php` 舊句。

## Good Example

- 這個例子是好的，因為無可修項與排除列分開，有可修項時每條都可委派。

```md
## 下一步建議

- 無可修項，不阻擋依 `tasks.md` 進入 `/implement`
- 排除（不委派）：不改 `plan.md`、`system-analyze/api-plan.md`、`system-analyze/technical-research.md` 的上游 Mock 舊句
```

```md
## 下一步建議

1. `/testplan` 只修 `BE-API-001B`、`FE-E2E-001B`（FR-003 預期值）
2. `/tasks` 只重開 `T008–T010`、`T020–T022`，其餘 `[X]` 保留
3. `/implement` 範圍 `T008–T010`、`T020–T022`
4. `/analyze` 再跑一次，確認清單項已消失
```

## Bad Example

- 這個例子是壞的，因為下一步是無法委派的長句，或叫人自己改檔。

```md
## 下一步建議

無嚴重發現。高項一致-1 是上游尚未跟上，不阻擋進入 /implement；實作時忽略 Mock，晚點再清 plan.md。
```
