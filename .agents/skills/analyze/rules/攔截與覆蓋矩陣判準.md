# Rule 1 - 必須做攔截檢查，且不得用舊三層當通過條件

- Level: `MUST`
  - 報告必須有「攔截檢查」表，至少涵蓋：
  - 缺切片（Slice）／任務（Task）／跨端旅程（Journey）
  - GWT 缺失
  - Mock 前端階段
  - 固定三層（後端／前端／整合）
  - `BE-REPO-*`
  - 舊三檔 task
  - 既有測試動作鏈
  - DDL／schema 工單
- 固定攔截列**不含** `my-specify`。指令名是 `/specify`；若要額外記指令名，攔截項寫 `specify`，不要寫舊前綴。
- 活 `testplan.md`／`tasks.md` 若仍要求契約 Mock、三檔 `task-plan/`、或 `BE-REPO-*`，必須記為**嚴重**或**高**，不可標通過。
- 上游 `plan.md`／`api-plan.md` 仍寫 Mock 但活 testplan／tasks 已改成真後端時，記為一致性發現，不得把 Mock 當本輪正確策略。

## Good Example

- 這個例子是好的，因為攔截項對準新控制平面。

```md
| Mock 前端階段 | 活產物通過；上游未清 | testplan／tasks 打真後端；plan／api-plan 仍寫 Mock |
| 舊三檔 task | 通過 | 控制平面是單一 tasks.md |
```

## Bad Example

- 這個例子是壞的，因為把前端 Mock 當成已拍板通過條件。

```md
| Mock 前端階段 | 通過 | 前端 Scenario 使用 API Mock，整合才停用 |
```

# Rule 2 - 覆蓋矩陣必須是需求 → 介面 → Slice → Task → Journey

- Level: `MUST`
- **規格覆蓋矩陣**欄位固定為：需求編號、摘要、實際介面、切片（Slice）、任務（Task）、旅程（Journey）。依 User Story 分表；全域約束可另表。
- **驗收覆蓋矩陣**欄位固定為：驗收／邊界、摘要、切片（Slice）、旅程（Journey）、備註。
- 不可再使用 Scenario／`S-n-m`、三層 Task 檔名，或「後端／前端／整合」打勾欄。
- 跨端故事若沒有 `FE-JOURNEY-*`（或等價旅程）與對應 `[ACCEPTANCE-GATE]`，記為嚴重或高。

## Good Example

- 這個例子是好的，因為欄位可直接對回 testplan／tasks。

```md
| 需求編號 | 摘要 | 實際介面 | 切片（Slice） | 任務（Task） | 旅程（Journey） |
| --- | --- | --- | --- | --- | --- |
| FR-005 | 確認前提供本筆預覽 | POST …/preview | BE-API-002A | T030–T032 | FE-JOURNEY-002 |
```

## Bad Example

- 這個例子是壞的，因為又回到三層打勾。

```md
| AC／Edge | Scenario | 後端 | 前端 | 整合 | Task 落點 |
| AC-1-1 | S-1-1 | ✓ | ✓ | ✓ | task-backend |
```

# Rule 3 - 嚴重程度指派啟發式

- Level: `MUST`
- **嚴重**：缺必備產物、plan 必跑介面缺檔、核心 FR／GWT 零切片且會阻斷基線功能、活產物仍用 Mock 前端或三檔 task、`DDL.md` 有新表但 `tasks.md` Foundational 沒有落地 `schema.sql` 的工單、明顯互相衝突且會讓實作做錯的約束、**產物明顯違反專案根 `constitution.md` 之 MUST**（有憲法檔時）
- **高**：上游與已鎖定 testplan／tasks 衝突（例如仍寫 Mock、`tests/run.php`）、介面契約互相矛盾、跨端故事缺 Journey
- **中**：次要覆蓋缺口、目錄結構過期、非基線路徑的對齊缺口
- **低**：不影響執行順序的輕微備註；第一版應少用
- 問題編號以比對依據字首＋序號，例如 `覆蓋-1`、`一致-2`。

## Good Example

- 這個例子是好的，因為高項指向會誤導實作的上游衝突，嚴重項才擋基線。

```text
高：plan.md／api-plan.md 仍寫前端 Mock，testplan 已要求打真後端
嚴重：US1 沒有任何 FE-JOURNEY 與 ACCEPTANCE-GATE
```

## Bad Example

- 這個例子是壞的，因為把標題用詞差異標成嚴重。

```text
嚴重：spec 寫「修改頁」、ui-plan 寫「更正頁」
```

# Rule 4 - 必須攔截錯的既有測試動作鏈，不得把覆蓋率 Add 或 Keep 當缺陷

- Level: `MUST`
- 攔截檢查必須含「既有測試動作鏈」列。對 `tasks.md` 與 `testplan.md` 比對：
  - Modify 切片沒有 `[TDD-ALIGN]` → 嚴重或高
  - 來源明文 Delete 卻沒有 `[TDD-REMOVE]` → 嚴重或高
  - Add 切片卻走 `[TDD-ALIGN]` → 嚴重或高
- 下列**不是**攔截失敗，也不得列為可修項：
  - `testplan.md` 沒有「測試修改類型」欄或測檔路徑
  - 本包沒重列的舊案例沒開工單（Keep）
  - Add 的 `[TDD-RED]` 標題沒寫「失敗」，或產品可能已符合目標案例（覆蓋率 Add）
- 不得建議把覆蓋率 Add 改成 Keep。

# Rule 5 - 必須攔截 DDL 增量未編成 schema 工單

- Level: `MUST`
- 攔截檢查必須含「DDL／schema 工單」列。對 `system-analyze/DDL.md`、現行 `app/config/schema.sql` 與 `tasks.md` Foundational 比對：
  - `DDL.md` 出現 `CREATE TABLE`，且該表名尚未出現在 `schema.sql`，但 Foundational 沒有落地 `app/config/schema.sql` 的任務 → 嚴重或高
  - 不得因 fixture 會 `CREATE TABLE IF NOT EXISTS` 而標通過
- 下列**不是**攔截失敗：
  - 本包無 `DDL.md` 或無 DB
  - `DDL.md` 的表已在現行 `schema.sql`，Foundational 無需再開 schema 工單
  - 只有 `ALTER`／升版且現行 schema 已一致

## Good Example

- 這個例子是好的，因為新表已編成 schema 工單，或現行 schema 已含該表。

```md
| DDL／schema 工單 | 通過 | DDL 新表已在 schema.sql；Foundational 無需再開工單 |
| DDL／schema 工單 | 失敗 | overtime_creation_drafts 不在 schema.sql，Foundational 只有 fixture |
```

## Bad Example

- 這個例子是壞的，因為把測具建表當成正式 schema 已落地。

```md
| DDL／schema 工單 | 通過 | T003 fixture 會 CREATE TABLE IF NOT EXISTS，不必改 schema.sql |
```

## Good Example

- 這個例子是好的，因為錯鏈才攔，覆蓋率 Add 放行。

```md
| 既有測試動作鏈 | 通過 | Modify 有 ALIGN；明文 Delete 有 REMOVE；Add 走 RED。BE-API-001C 屬覆蓋率 Add，不改 Keep |
```

## Bad Example

- 這個例子是壞的，因為把合法覆蓋率或 Keep 當成要修的缺陷。

```md
| 既有測試動作鏈 | 失敗 | 001C 產品已會 400，應改成 Keep、刪 RED 工單 |
| 既有測試動作鏈 | 失敗 | testplan 沒有「測試修改類型」欄 |
```
