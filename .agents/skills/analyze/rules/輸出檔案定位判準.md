# Rule 1 - 最終分析報告必須寫到 package 根目錄固定檔名

- Level: `MUST`
- `/analyze` 的最終產物路徑固定為 `specs/<NNN-plan-package>/analyze-report.md`。
- 本 skill **不 WRITE** 來源規格、`testplan.md`、`tasks.md` 與選備介面；允許寫入或更新的檔案只有 `analyze-report.md`。
- 使用者回「修」後，來源檔只准由被 DELEGATE 的 writer skill 修改，不算出 analyze 自己寫入。
- 不可把完成稿只留在聊天訊息、暫存筆記、`system-analyze/` 或其他任意檔名中。

## Good Example

- 這個例子是好的，因為報告與 `spec.md`、`testplan.md`、`tasks.md` 同層。

```text
specs/001-overtime-correction/analyze-report.md
```

## Bad Example

- 這個例子是壞的，因為報告藏在介面合約目錄。

```text
specs/001-overtime-correction/system-analyze/analyze-report.md
```

# Rule 2 - `plan-package` 必須與上游 spec 目錄對齊

- Level: `MUST`
- `plan-package` 必須沿用同功能的 `specs/<NNN-plan-package>/` 目錄名。
- 若使用者已指定既有 package，應寫入該 package 根目錄，不可另開平行目錄。

## Good Example

- 這個例子是好的，因為分析報告與規格鏈落在同一 package。

```text
specs/001-overtime-correction/spec.md
specs/001-overtime-correction/analyze-report.md
```

## Bad Example

- 這個例子是壞的，因為報告與規格分散在不同 package。

```text
specs/001-overtime-correction/spec.md
specs/002-misc/analyze-report.md
```

# Rule 3 - 標題與小標必須對齊同 package 契約

- Level: `MUST`
- H1 固定為 `# 規格分析報告：{{FEATURE_NAME}}`，功能中文名與同 package 的 `spec.md` 對齊。
- 小標固定三行：`**功能分支**:`、`**建立日期**:`、`**狀態**:`；功能分支值以 inline code 包住，且與 `plan-package` 相同。
- `**建立日期**:` 使用本次產出日期（`YYYY-MM-DD`）；`**狀態**:` 第一版預設 `草稿`。

## Good Example

- 這個例子是好的，因為標題與小標可直接對回目錄與其他規格產物。

```md
# 規格分析報告：加班資料與計薪方式更正功能

**功能分支**: `001-overtime-correction`
**建立日期**: 2026-09-04
**狀態**: 草稿
```

## Bad Example

- 這個例子是壞的，因為缺少功能分支，且標題無法對回 package。

```md
# Analysis Report

**日期**: 2026-09-04
```
