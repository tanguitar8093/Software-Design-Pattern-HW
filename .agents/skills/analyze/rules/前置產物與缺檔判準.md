# Rule 1 - 必備產物齊全才能進入 inventory

- Level: `MUST`
- 進入 Phase 2 前，下列產物必須存在於同 package：
  - `spec.md`
  - `testplan.md`
  - `tasks.md`
- 任一必備產物缺失時，必須停止分析，並指示使用者先完成對應 skill（`/specify`、`/testplan`、`/tasks`），不可自行腦補缺檔內容。
- 不可把 `e2e-test-plan.md` 或 `task-plan/task-backend.md`／`task-frontend.md`／`task-integration.md` 當成必備。那些檔不存在時不得報「缺必備產物」。

## Good Example

- 這個例子是好的，因為缺 `tasks.md` 時明確停住並指路。

```text
缺：specs/001-overtime-correction/tasks.md
→ 停止 /analyze，請先完成 /tasks
```

## Bad Example

- 這個例子是壞的，因為把已刪除的三檔 task 當成必備缺檔。

```text
缺：task-plan/task-backend.md
→ 停止 /analyze，請先完成 /task-plan
```

# Rule 2 - 選備介面產物依實際存在與 plan 意圖計分

- Level: `MUST`
- 下列為選備產物，存在才納入 inventory 與覆蓋檢查：
  - `plan.md`
  - `system-analyze/technical-research.md`
  - `system-analyze/data-plan.md`
  - `system-analyze/DDL.md`（有 DB 時）
  - `system-analyze/api-plan.md`
  - `system-analyze/ui-plan.md`
- 若 `plan.md`（或 research）明示本次應產出某介面，但對應檔案不存在，必須記為**嚴重**發現（缺必跑介面），不可當「選填跳過」略過。
- 若 plan 未要求該介面且檔案不存在，不計入覆蓋分母，也不報缺檔。

## Good Example

- 這個例子是好的，因為只對「本次應有」的介面要求存在。

```text
plan 標示需要 API 與 UI；api-plan.md 存在、ui-plan.md 缺失
→ 嚴重：缺 ui-plan.md
```

## Bad Example

- 這個例子是壞的，因為把未規劃的 DDL 也當成缺檔嚴重項。

```text
本功能無 DB，卻因沒有 DDL.md 報嚴重缺檔
```

# Rule 3 - 缺檔說明必須可執行

- Level: `SHOULD`
- 停止或嚴重缺檔時，應寫出缺哪個路徑、建議執行哪個 skill，避免只寫「資料不齊」。

## Good Example

- 這個例子是好的，因為路徑與指令都清楚。

```text
缺少 specs/001-overtime-correction/testplan.md
請先執行 /testplan
```

## Bad Example

- 這個例子是壞的，因為無法據此補跑。

```text
前置條件不足，請檢查規格。
```
