# Rule 1 - 對話最後一行必須是下一步

- Level: `MUST`
- `/analyze` 對話最後一行必須單獨寫下一步，不得埋在中間句子。
- 無可修項時，最後一行固定為：下一步：實作 /implement
- 有可修項、尚未收到「修」時，最後一行固定為：下一步：等待確認是否依上表修補（回「修」）
- 同一批可修項修完仍原樣出現、停止打轉時，最後一行為：下一步：等待 <仍未消除的原因>
- 禁止「1. 先修 2. 或直接實作」這種可跳過雙門。有可修項時只問是否依上表修補，不問要不要跳過清單直接實作。

## Good Example

- 這個例子是好的，因為無可修項時最後一行清楚放行實作。

```md
報告已寫入 `specs/001-overtime-correction/analyze-report.md`。無可修項。

下一步：實作 /implement
```

## Bad Example

- 這個例子是壞的，因為下一步是可跳過雙門，或沿用舊測試／任務指令。

```md
建議下一步
1. 修嚴重項
2. 或直接 /implement
請先重跑 /e2e-test-plan 與 /task-plan
```

# Rule 2 - 有可修項時必須列出 skill＋範圍並等待「修」，不得自己改來源檔

- Level: `MUST`
- 若報告含可修項：收尾與報告皆須列出有序的 skill、檔案與 ID 範圍，並請使用者回「修」後才依序 DELEGATE。
- 必須點名呼叫哪個 skill、改哪些 ID；不可寫「請自行檢查」，也不可建議人手動改來源檔。
- 未收到「修」或等價同意前，不得開始委派，也不得 WRITE `spec.md`、`testplan.md`、`tasks.md` 或介面計畫檔。
- 第一次建置且無可修項時，不要問「要不要幫忙修改」。

## Good Example

- 這個例子是好的，因為可修項變成可執行清單，並停在確認。

```md
偵測到 1 項可修項，請回「修」以依序委派：
1. /testplan 只修 BE-API-001B、FE-E2E-001B（FR-003 預期值）
2. /tasks 只重開 T008–T010、T020–T022，其餘 [X] 保留
3. /implement 範圍 T008–T010、T020–T022
4. /analyze 再跑一次，確認清單項已消失

下一步：等待確認是否依上表修補（回「修」）
```

## Bad Example

- 這個例子是壞的，因為有可修項仍直接放行實作，或叫人自己改檔。

```md
US1 缺旅程。請手動修改 testplan.md 後自行重跑 /tasks。
下一步：實作 /implement
```

# Rule 3 - 無可修項時可建議進入實作，仍應提示剩餘風險

- Level: `SHOULD`
- 若僅有排除列（不委派）的高／中／低發現，或完全無發現：可建議 Review 報告後執行 `/implement`。
- 若仍有高／中項被列為排除，應在重點摘要條列，避免靜默當成完美通過。

## Good Example

- 這個例子是好的，因為放行實作但仍可見剩餘風險。

```md
無可修項，可進 /implement。
剩餘風險：高 1 項已列入排除，上游 plan／api-plan 仍寫 Mock。
```

## Bad Example

- 這個例子是壞的，因為有高優先缺口卻完全不提。

```md
分析完成，一切正常，請直接實作。
```

# Rule 4 - 產物表只列本輪實際寫入的分析報告

- Level: `MUST`
- 對話若列出本輪產物，應列出本次新增或更新的 `analyze-report.md`。
- 不可把唯讀讀過的 `spec.md`、`testplan.md`、`tasks.md` 假裝成本輪新增產物。
- 委派 writer 之後，那些檔案是被委派 skill 寫入的，不要寫成 analyze 本輪新增產物。

## Good Example

- 這個例子是好的，因為產物表與實際寫入一致。

```md
| 產物 | 路徑 | 說明 |
| --- | --- | --- |
| 規格分析報告 | specs/001-overtime-correction/analyze-report.md | 覆蓋與攔截檢查 |
```

## Bad Example

- 這個例子是壞的，因為把輸入檔當成產出。

```md
| 產物 | 路徑 |
| --- | --- |
| 規格 | specs/001-overtime-correction/spec.md |
| 測試計畫 | specs/001-overtime-correction/testplan.md |
```
