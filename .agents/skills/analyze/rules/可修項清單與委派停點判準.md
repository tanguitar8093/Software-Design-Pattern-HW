# Rule 1 - 可修項必須能對到 writer skill 與 ID 範圍

- Level: `MUST`
- 可修項是會讓實作做錯、且應由下游 skill 改檔的發現：缺切片／旅程／任務、GWT 與案例對不齊、核心 FR 零切片、活產物仍用 Mock 或三檔 task、`DDL.md` 新表未編成 `schema.sql` Foundational 工單、規格改了但 testplan／tasks 未跟上。
- 每一項可修項必須能寫成「呼叫哪個 skill、改哪個檔、哪些 ID、做什麼」。
- 不可把「請自行檢查」或「人手動改 Markdown」當成可修項的處理方式。

## Good Example

- 這個例子是好的，因為發現可以直接變成委派範圍。

```md
覆蓋缺口：FR-003 預期值已改，BE-API-001B／FE-E2E-001B 仍寫舊規則
→ /testplan 只修 BE-API-001B、FE-E2E-001B
→ /tasks 只重開 T008–T010、T020–T022
```

## Bad Example

- 這個例子是壞的，因為沒有 skill 與 ID，無法委派。

```md
規格好像有點不一致，請自行檢查相關檔案。
```

# Rule 2 - 排除列不得進入委派清單

- Level: `MUST`
- 下列發現寫入排除（不委派），不得因它們去問「修」，也不得 DELEGATE：
  - 已聲明不改的上游活包舊句（`plan.md`、`system-analyze/technical-research.md` 的 Mock／`tests/run.php` 歷史句）
  - 已接受為體驗指標、不另開切片的 NFR
  - 報告過期說明，而非缺檔
  - `testplan.md` 沒有「測試修改類型」欄或既有測檔路徑
  - 沒重列的舊案例沒開工單（Keep）
  - Add 的 RED 一寫就綠、產品已符合目標案例（覆蓋率 Add；不得改成 Keep）
- 排除列可留在報告提醒實作忽略，但不能出現在「回修後要執行」的有序清單裡。

## Good Example

- 這個例子是好的，因為上游舊句被排除，不問修、不委派。

```md
可修項：無
排除（不委派）：不改 plan.md、system-analyze/api-plan.md、system-analyze/technical-research.md 的上游 Mock 舊句
```

## Bad Example

- 這個例子是壞的，因為把已聲明不改的上游舊句拿來問使用者要不要修。

```md
1. /technical-research 重寫 Mock 舊句
請回「修」
```

# Rule 3 - 委派必須上游先於下游、一次一個 skill，且不得自己改來源檔

- Level: `MUST`
- 收到「修」後，依清單順序 DELEGATE：較上游的規格／介面先於 `testplan`，`testplan` 先於 `tasks`，`tasks` 先於 `/implement`。
- 一個 skill 完成（含其 validator）後才呼叫下一個。
- 本 skill 不得 WRITE `spec.md`、`testplan.md`、`tasks.md` 或 `system-analyze/` 介面檔；那些檔只准由被委派的 skill 修改。
- 交付給 writer 時必須帶 package、ID 範圍，以及「只修補、保留未點名章節與 `[X]`」。

## Good Example

- 這個例子是好的，因為順序與改檔責任都正確。

```md
1. DELEGATE /testplan（只修 BE-API-001B、FE-E2E-001B）
2. 等 validator 通過
3. DELEGATE /tasks（只重開 T008–T010、T020–T022，其餘 [X] 保留）
4. DELEGATE /implement（範圍同上）
5. 返回 Phase 2 再分析
```

## Bad Example

- 這個例子是壞的，因為 analyze 自己改了 testplan，或一次並行呼叫造成範圍打架。

```md
直接覆寫 testplan.md 兩則案例，同時開 /tasks 與 /implement。
```

# Rule 4 - 再分析不得把排除列或剛修過仍原樣的項拿來打轉

- Level: `MUST`
- 清單中的「再跑 `/analyze`」是返回 Phase 2 更新同一份報告，不是再 spawn 一個 analyze 實例、也不是本 skill WRITE 來源檔。
- 再分析後，排除列不得重新變成可修項。
- 若同一批可修項在 writer 已跑完後仍原樣出現，停止再委派，最後一行改為等待仍未消除的原因。

## Good Example

- 這個例子是好的，因為第二輪只檢查清單項是否消失，不重提排除列。

```md
再分析後：BE-API-001B 已對齊 FR-003；排除列 Mock 舊句仍在但不提案。
下一步：實作 /implement
```

## Bad Example

- 這個例子是壞的，因為第二輪又拿「不改上游 Mock」來問修，形成打轉。

```md
再分析後仍有一致-1 上游 Mock，請回「修」以重寫 plan.md。
```
