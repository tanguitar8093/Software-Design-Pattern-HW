# Rule 1 - 憲法只寫專案級、high-level、可判定的規範

- Level: `MUST`
- 條文 MUST 是跨功能、專案級約束，且讀者能以是／否判斷是否遵守。
- 禁止寫入單一功能需求、具體 API path／HTTP 欄位表、具體 UI 畫面欄位或單一 User Story 細節（那些屬 `specs/<package>/` 產物）。
- 技術約束可具體到堆疊與禁准項（例如允許的框架、是否禁 ORM），但不可下沉成某次功能的 schema／endpoint 清單。

## Good Example

- 這個例子是好的，因為約束可判定且保持抽象層正確。

```md
- MUST：前端執行期不引入 React／Vue 等 UI framework。
- MUST：前後端（若皆存在）以 REST API 為唯一整合介面。
```

## Bad Example

- 這個例子是壞的，因為把單一功能合約細節寫進憲法。

```md
- POST /api/albums 的 body 必須含 name 欄位。
- 相簿詳情頁縮圖格子為三欄。
```

# Rule 2 - 固定章節順序與必要標題

- Level: `MUST`
- 正文 MUST 依序包含以下二級標題（可在其下使用條列）：`## 核心原則`、`## 技術約束`、`## 流程與品質規範`、`## 憲法規範效力`。
- 不可刪除上述必要章節；MAY 在效力章之後新增補充章節，但不得插入打亂上述四章順序。
- H1 與 metadata 之後、第一個必要章節之前，MAY 有一段簡短定位說明（非必須）。

## Good Example

- 這個例子是好的，因為四個必要章節齊全且順序正確。

```md
## 核心原則
## 技術約束
## 流程與品質規範
## 憲法規範效力
```

## Bad Example

- 這個例子是壞的，因為缺章或順序錯亂。

```md
## 技術約束
## API 詳細規格
## 核心原則
```

# Rule 3 - 修訂時必須更新最後修訂；語意變更必須升版本

- Level: `MUST`
- 任何寫入／修訂成功後，`**最後修訂**:` MUST 更新為當日 `YYYY-MM-DD`。
- 若變更改變規範語意（新增／刪除／重寫 MUST 條文、改變技術基線或流程關卡），`**版本**:` MUST 遞增：不相容的原則重定義升 MAJOR；新增原則／章節或實質擴充升 MINOR；錯字、措辭澄清、不改變義務的潤飾升 PATCH（或僅更新日期且版本不變，僅限純澄清）。
- 新建時：`建立日期` 與 `最後修訂` 皆為當日；版本預設 `` `1.0.0` ``，除非使用者另行指定。

## Good Example

- 這個例子是好的，因為語意變更有升版，且更新日期。

```text
新增「禁止 ORM」MUST → 版本 1.0.1 → 1.1.0，最後修訂改為今日
只改錯字 → 最後修訂改今日，版本可維持或 +PATCH
```

## Bad Example

- 這個例子是壞的，因為改了硬性約束卻不升版、不改日期。

```text
把「禁止 ORM」改成「允許 ORM」，版本與最後修訂都不動
```

# Rule 4 - 效力章必須保留憲法優先與本 skill 維護邊界

- Level: `MUST`
- `## 憲法規範效力` MUST 表達：本規範優先於各 skill 預設慣例；衝突時以本規範為準。
- MUST 表明本檔可由人工或 `/constitution` 維護，且 V1 不要求修訂時同步其他 skill／templates。
- SHOULD 保留「交付向 skill 若約定讀取本檔：有則遵守；缺檔時依專案約定警告後繼續」之類表述，與專案已拍板策略一致。

## Good Example

- 這個例子是好的，因為效力、維護方式與不同步邊界都清楚。

```md
## 憲法規範效力

- 本規範優先於各 skill 之預設慣例；衝突時以本規範為準。
- 本檔由人工編輯或 `/constitution` 建立／修訂；……
- V1 不要求修訂本檔時同步修改其他 skill 或 templates；……
```

## Bad Example

- 這個例子是壞的，因為效力章要求每次改憲法都自動改全部 skill。

```md
## 憲法規範效力

- 每次修訂 MUST 同步更新所有交付 skill 的 SOP。
```
