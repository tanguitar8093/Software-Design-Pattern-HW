# Rule 1 - 進場必須帶齊 package、故事、案例與剩餘步驟

- Level: `MUST`
- 只接受 `/implement` 以 Task 子代理、針對單一切片的委派；必須提供：`plan-package`（僅目錄名，不含 `specs/`）、task 標題上的 `US#`、`CASE_ID`、`remaining_steps`（有序清單）。
- `CASE_ID` 必須對得上 `tasks.md` 標題的 `[SLICE …]` 與 `testplan.md` 該則案例；一次進場只處理這一則切片。
- `remaining_steps` 只能是該切片尚未勾選的步驟，且順序必須是 `RED` → `GREEN` → `REFACTOR`，或 `ALIGN` → `GREEN` → `REFACTOR`。不得跳過中間步驟，不得帶入其他 `CASE_ID`。
- 缺欄位時停止並回報，不可猜測 `layer`、不可把整個 User Story 當成本輪，也不可沿用已刪除的 `S-n-m`／Scenario Agent 契約。

## Good Example

- 這個例子是好的，因為呼叫欄位對上單一切片與其剩餘鏈。

```md
plan-package: 003-overtime-create
US#: US1
CASE_ID: FE-E2E-001C
remaining_steps: RED, GREEN, REFACTOR
對應 task：T026 [TDD-RED]、T027 [TDD-GREEN]、T028 [TDD-REFACTOR]
```

## Bad Example

- 這個例子是壞的，因為沿用舊層別契約，或一次帶整段故事。

```md
layer: backend
請把 US1 全部 Red 做完
或 remaining_steps 只寫 GREEN，卻還沒做本切片 RED
```

# Rule 2 - 只接受 `/implement` 切片委派，禁止單獨進場

- Level: `MUST`
- `/tdd` 不會被單獨呼叫；只由 `/implement` 在 `[TDD-*]` 切片任務內以 Task 子代理委派。子代理進場必須先讀 `.agents/skills/tdd/SKILL.md`。
- 本輪必須依 `remaining_steps` 在同一執行體內依序做完，不得把下一步交回再開一次子代理，也不得做清單以外的步驟。
- 若人直接呼叫 `/tdd`，停止並回報改走 `/implement`，不得自行選切片。
- 本 skill 不代勾 `tasks.md`；做完把各步驟證據交回 `/implement` 勾選。

## Good Example

- 這個例子是好的，因為 implement 委派整條剩餘鏈，子代理依序做完再交回。

```md
委派 `/tdd`：CASE_ID=BE-API-001A，remaining_steps=RED,GREEN,REFACTOR
子代理先寫測、再最小實作、再整理，一次交回三段證據
```

## Bad Example

- 這個例子是壞的，因為做完 RED 就停下來等父代理再開 GREEN 子代理。

```md
remaining_steps=RED,GREEN,REFACTOR
RED 合格後立即交回，不進入 GREEN
或順便把下一切片 BE-API-001B 也做完
```

# Rule 3 - Setup、Foundational 與 Journey 不是 `/tdd` 的工作

- Level: `MUST`
- 若 `CASE_ID` 是 `FE-JOURNEY-*`，或 task 帶 `[ACCEPTANCE-GATE]`，或任務屬於 Setup／Foundational，必須拒絕並交回 `/implement`。
- 若 `CASE_ID` 是 `FE-E2E-*` 且 `remaining_steps` 含 `RED` 或 `ALIGN`，對應同故事 `BE-API-*` 的 `[TDD-GREEN]` 必須已勾；未勾則停止，不得先用契約 Mock 起跑。
- 不得為了「先寫測」而建立正式測試入口；那是 Setup 任務。

## Good Example

- 這個例子是好的，因為它只接受切片 TDD，並守住前端不得早於 API 綠燈。

```md
接受：BE-API-001A remaining_steps=RED,GREEN,REFACTOR
接受：FE-E2E-001A remaining_steps=RED,GREEN,REFACTOR（且 BE-API-001A GREEN 已 [X]）
拒絕：FE-JOURNEY-001 ACCEPTANCE-GATE
拒絕：T001 建立 PHPUnit 入口
```

## Bad Example

- 這個例子是壞的，因為它把驗收旅程或環境建立當成一輪紅燈。

```md
對 FE-JOURNEY-001 寫一支 TDD RED
或在 T001 尚未完成時，自行建立 tests/e2e 並開始 FE-E2E RED
```

# Rule 4 - 只讀本切片 Must Read，seam 能導出就不必問人

- Level: `MUST`
- 進場只讀該切片 `tasks.md` 必讀（Must Read）指向的 `testplan.md` 案例；後端切片再讀所列 `api-plan.md` 契約，一則契約一列。同一切片三則工單的必讀應取聯集，仍不得改讀下一切片。
- 不得重開 `testplan.md` 全文定位，也不得把選讀（Optional）當成必讀。
- 若 public seam、oracle 與 out-of-scope 能從該案例的受測部位、操作（Act）輸入、觀測通道／預期輸出導出，必須直接凍結並繼續；只有導不出來時才停下問人。

## Good Example

- 這個例子是好的，因為它只讀本則案例就把 seam 凍結好。

```md
必讀：
- testplan.md -> ### BE-API-001A - 送出遠峰範例更正並取得預覽
- api-plan.md -> 對應預覽契約

凍結：
- public seam：預覽 API HTTP
- oracle：回傳本筆前後差異，正式資料尚未生效
```

## Bad Example

- 這個例子是壞的，因為它整份通讀 testplan，或明明案例已寫清仍停下來問 seam。

```md
先把 testplan.md 從頭讀到尾
再問使用者「這輪要測哪個 API？」
```

# Rule 5 - 收尾必須交出各步驟證據，且對話最後一行寫下一步

- Level: `MUST`
- 完成回報必須依 `remaining_steps` 分段，每段至少包含：測檔路徑、執行指令、該步驟的紅燈／綠燈／整理原因（對準本則主斷言或行為）。
- 環境不可執行、或測映射不出本則 testplan 時，停止並把阻塞交回 `/implement`，不得假裝進入 GREEN。
- 產品已符合目標案例、新測 mapping 對且已綠時，**不是**阻塞；在同一執行體內繼續 GREEN（可無實作）與 REFACTOR（可無重構）。不得因已綠建議改成 Keep 或回頭改 `tasks.md`。
- 對話最後一行必須單獨寫「下一步：交回實作編排 /implement」。

## Good Example

- 這個例子是好的，因為三段證據夠讓 implement 勾三則，且最後一行清楚交回。

```md
CASE_ID: BE-API-001A
RED：測檔 …/BeApi001APreviewTest.php；指令 … --filter BeApi001A；紅燈＝尚未回傳前後差異
GREEN：同測轉綠；最小實作接上預覽契約
REFACTOR：本則無重構；測仍綠

下一步：交回實作編排 /implement
```

## Bad Example

- 這個例子是壞的，因為它自己勾選 task，或只交 RED 就結束。

```md
已把 T005–T007 改成 [X]
看起來紅了，請繼續
```
