# Rule 1 - 行為變更預設使用 TDD，例外必須明確說出理由

- Level: `MUST`
- 只要任務會新增行為、修正 bug、改變既有輸出、補 edge case，或要求用測試證明結果，就預設走 TDD。
- 若任務屬於 throwaway prototype、純設定調整、純文件、生成檔、或主要驗證必須依賴昂貴人工檢查，才可不走完整 TDD；此時必須先向使用者說明原因與替代驗證方式。
- 不可因為「趕時間」「應該很簡單」或「先寫再補測試比較快」而跳過測試。已綠覆蓋率不是跳過紅燈：測已寫、mapping 對、產品已符合。不得把「不可跳過紅燈」讀成必須先改壞產品。

## Good Example

- 這個例子是好的，因為它把 TDD 當預設，只有在例外情境才明確偏離並交代原因。

```md
任務：修正折扣計算在滿額邊界少算 1 元的 bug

決策：
- 這是既有行為修正，必須先寫重現 bug 的 failing test

任務：調整 README 內的安裝說明

決策：
- 這不是行為變更，不走 TDD
- 替代驗證：檢查指令與目錄路徑是否與現況一致
```

## Bad Example

- 這個例子是壞的，因為它把「方便」當成例外理由，直接略過紅燈。

```md
任務：新增重試機制

決策：
- 先把程式寫完，之後如果有空再補測試
- 理由：這功能看起來很直覺
```

# Rule 2 - 驗證若太慢或 oracle 不清楚，先縮小 seam 與切片

- Level: `SHOULD`
- 若完整驗證很慢、很脆弱，或需求還沒有清楚到能寫出可執行 oracle，應先縮小到較小的 public seam 或更薄的 vertical slice，再進入 RED。
- 若縮小後仍無法得到可信紅燈，應停下來補對齊需求或改變驗證策略，不要用模糊斷言假裝自己在做 TDD。
- TDD 的前提是「能用測試證明」，不是「能寫一段長得像測試的程式」。

## Good Example

- 這個例子是好的，因為它先把驗證問題收斂成可執行的 slice，再開始寫測試。

```md
觀察：
- 端到端流程要 8 分鐘，且需求只先確定輸入驗證規則

調整：
- 先把 seam 縮到 `validateSignupInput()`
- 先測 email 與密碼格式規則，不先碰整段註冊流程
```

## Bad Example

- 這個例子是壞的，因為需求與 oracle 都模糊，卻硬寫出沒有證明力的測試。

```md
觀察：
- 使用者只說「讓 dashboard 感覺更快」

做法：
- 直接寫 `expect(pageFeelsFast).toBe(true)`
- 不先拆成可量測的行為或性能門檻
```
