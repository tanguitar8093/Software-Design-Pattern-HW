# Rule 1 - 沒證明測試會抓到缺口前，不得寫 production code

- Level: `MUST`
- 每一輪若產品尚未符合本則目標案例，必須先寫測試、親自執行、看見它因為「尚未實作的行為」而失敗，之後才能進入 production code。
- 若產品已符合目標案例，RED 的新測可以已綠；此時本輪與後續 GREEN 都不得為了「補一個紅燈」去改產品碼。
- 若先偷寫了 production code，即使只是「先當參考」，也應刪掉後重新從測試開始。
- 沒看到紅燈就改產品碼，等同沒有證明測試真的會抓到缺口。已綠覆蓋率不在此列：那裡本來就沒有缺口。

## Good Example

- 這個例子是好的，因為它先拿到對準缺口的紅燈，再開始寫最小實作。

```md
順序：
1. 寫一個驗證 `retry 只重試 3 次` 的測試
2. 執行測試，看到因為尚未有 retry 邏輯而失敗
3. 才開始補最小實作
```

## Bad Example

- 這個例子是壞的，因為它把實作寫在前面，紅燈只剩形式意義。

```md
順序：
1. 先把 retry 邏輯大致寫完
2. 再補測試確認它現在是綠的
3. 說自己有遵守 TDD
```

# Rule 2 - 一次只做一個 vertical slice，不做 horizontal slicing

- Level: `MUST`
- 每一輪只允許一個 seam、一個主要行為、一個測試、一個最小實作。
- 不可先把所有測試一次鋪完，再回頭補所有實作；那會讓測試驗證想像中的設計，而不是與實作互相校正。
- 每個 slice 都應像 tracer bullet：用最小可驗證行為推進設計，而不是先承諾整個架構。

## Good Example

- 這個例子是好的，因為它用一個薄切片推進對外能力。

```md
切片順序：
1. 先讓 `createUser()` 能建立最簡單的有效使用者
2. 下一輪再處理重複 email
3. 再下一輪才處理歡迎信
```

## Bad Example

- 這個例子是壞的，因為它把所有情境一起鋪開，測試與實作都失去回饋節奏。

```md
切片順序：
1. 先把建立使用者、重複 email、歡迎信、權限檢查的所有測試一次寫完
2. 再開始一次補齊全部 production code
```

# Rule 3 - GREEN 只寫剛好通過本輪紅燈的最小實作

- Level: `MUST`
- GREEN 的目標是把目前紅燈轉綠，不是順便把下一輪也做完。
- 不可預作未來 edge case、先塞抽象層、先加還沒被測到的條件分支，或把需求尚未確認的行為一起實作。
- 若發現自己正在寫「反正等等大概也會需要」，應先停手，刪回到本輪測試真正要求的最小版本。

## Good Example

- 這個例子是好的，因為它只滿足當前測試需要的能力。

```md
當前紅燈：
- 有效購物車可成功 checkout

GREEN：
- 只補成功結帳所需最小流程
- 不先處理過期優惠券、庫存不足、寄信通知
```

## Bad Example

- 這個例子是壞的，因為它在第一輪就把後面還沒被要求的行為全部做進去。

```md
當前紅燈：
- 有效購物車可成功 checkout

GREEN：
- 一次加入折扣規則、庫存同步、通知、補償交易、分析事件
```

# Rule 4 - refactor 只能在綠燈後進行，且不得擴大需求範圍

- Level: `SHOULD`
- 只有在目前相關測試已全部綠燈時，才做命名調整、重複消除、小幅抽取等 behavior-preserving cleanup。
- 若整理已牽涉新設計取捨、跨模組重構或新需求切片，應停止並回報使用者，而不是把 refactor 當成偷偷擴 scope 的藉口。
- refactor 完成後必須重新執行受影響測試，確認仍然維持綠燈。

## Good Example

- 這個例子是好的，因為它把整理限制在不改變行為的安全範圍內。

```md
綠燈後整理：
- 重新命名變數
- 抽出重複的純函式
- 刪除本輪產生的重複判斷
- 再跑一次相關測試
```

## Bad Example

- 這個例子是壞的，因為它把 refactor 當成加入新設計與新需求的入口。

```md
綠燈後整理：
- 順手把整個 module 改成事件驅動架構
- 一起換資料庫 schema
- 再補兩個還沒談好的需求
```
