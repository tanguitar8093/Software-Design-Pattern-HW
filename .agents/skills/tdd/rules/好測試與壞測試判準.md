# Rule 1 - 好測試描述使用者或呼叫者在乎的行為

- Level: `MUST`
- 測試名稱與斷言都應描述 `WHAT`，不是 `HOW`。
- 好測試應透過 public seam 驗證可觀測行為，讓內部實作就算重構，測試也仍然成立。
- 預期值必須來自獨立 oracle，例如已知字面值、明確規格、人工算例或對外契約，而不是跟著實作一起重算。

## Good Example

- 這個例子是好的，因為它描述對外行為，且預期值不是從實作邏輯重算出來的。

```md
測試名稱：
- `使用有效購物車可完成結帳`

斷言：
- `checkout(cart, paymentMethod)` 回傳 `status = confirmed`

另一個例子：
- `calculateTotal([{ price: 10 }, { price: 5 }]) === 15`
```

## Bad Example

- 這個例子是壞的，因為它把測試寫成對實作細節的旁證，或用同一套邏輯重算 expected。

```md
測試名稱：
- `checkout 會呼叫 paymentService.process`

斷言：
- 驗證 internal collaborator 的 call count 與參數

另一個例子：
- `expected = items.reduce(...)`
- `expect(calculateTotal(items)).toBe(expected)`
```

# Rule 2 - implementation-coupled 測試必須視為錯誤方向

- Level: `MUST`
- 出現下列訊號時，應判定測試過度耦合實作：mock 自家 internal collaborator、直接測 private method、依賴 call order / call count、或只要重構就會壞但行為其實沒變。
- 一旦發現 implementation-coupled 測試，應先回到 seam 與 oracle 重新設計測試，不可硬著頭皮沿用。
- 若測試的重點只能用「因為我知道它裡面怎麼做」來解釋，這通常就是錯的。

## Good Example

- 這個例子是好的，因為它只關心對外能力，沒有把內部協作者變成測試主角。

```md
需求：
- 建立使用者後應可被讀回

測試：
- `user = createUser({ name: "Alice" })`
- `retrieved = getUser(user.id)`
- `expect(retrieved.name).toBe("Alice")`
```

## Bad Example

- 這個例子是壞的，因為它把內部協作者或私有方法當成成功條件。

```md
需求：
- 建立使用者後應可被讀回

測試：
- mock `UserRepository.save`
- 驗證 `save` 被呼叫一次
- 或直接測 `UserService._normalizePayload()`
```

# Rule 3 - tautological 測試不能當作有效證明

- Level: `MUST`
- 若 expected value 是用與實作相同的運算、分支或映射重新算出來，測試就會「天生同意」實作，不能算有效證明。
- 預期值必須能在不相信當前實作的前提下成立。
- 若真的找不到獨立 oracle，先回頭釐清需求、舉例或拆更小的案例，不要硬寫 tautological test。

## Good Example

- 這個例子是好的，因為預期值是獨立且可直接判斷的。

```md
案例：
- `calculateTotal([{ price: 10 }, { price: 5 }]) === 15`
- `retryCount` 上限為 `3`
- 狀態轉移後應回傳 `archived`
```

## Bad Example

- 這個例子是壞的，因為 expected 跟實作共享同一套推導方式。

```md
案例：
- `expected = items.reduce((sum, i) => sum + i.price, 0)`
- `expected = normalize(input).trim().toLowerCase()`
- 再拿這些 expected 去驗證同一個邏輯的函式
```

# Rule 4 - 一輪只寫一個可讀、可診斷的測試

- Level: `SHOULD`
- 每個 test 預設只承擔一個主要行為斷言，讓紅燈原因與綠燈意義保持清楚。
- 若同一個測試同時涵蓋成功路徑、錯誤路徑、邊界值與多個條件分支，通常表示應切成多個 vertical slices。
- 測試內容應讓人一眼看出 Arrange、Act、Assert 的結構；若本輪有新增、修改或重寫真實測試檔，應依 `rules/測試結構與3A註解格式.md` 使用一致的 3A 註解格式。

## Good Example

- 這個例子是好的，因為它把單一案例講清楚，出錯時也容易定位。

```md
測試：
- 建立一個有效購物車
- 執行 `checkout`
- 只斷言結果是 `confirmed`
```

## Bad Example

- 這個例子是壞的，因為它把太多案例塞進同一輪，導致紅燈不知是在說哪件事。

```md
測試：
- 同時驗證成功結帳、付款失敗、優惠券過期、庫存不足、寄信通知
- 任何一處失敗都會讓整個測試一起紅
```
