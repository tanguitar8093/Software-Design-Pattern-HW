# Rule 1 - 故事專屬 FR 必須掛在該故事下，編號用全域唯一 FR-nnn

- Level: `MUST`
- 主要只支撐單一使用者價值的 `FR`，必須寫在該 User Story 的 `**功能需求（FR）**:` 底下。
- 編號使用全域唯一的 `FR-001`、`FR-002`…，不要用 `US1-FR1`。
- 不可把故事專屬需求再抄一份到全域，也不可改用 `GR-xxx`。

## Good Example

- 這個例子是好的，因為需求掛在故事下，且編號是全域唯一。

```md
### User Story 1 - 在現有後台更正加班資料與計薪方式 (Priority: P1)

**功能需求（FR）**:

- **FR-001**: 系統 MUST 在現有後台提供加班更正修改頁。
- **FR-002**: 系統 MUST 允許在同一更正流程中調整該筆加班所屬員工的時薪。
```

## Bad Example

- 這個例子是壞的，因為用了故事內流水號，之後無法一路對到測檔。

```md
**功能需求**

- **US1-FR1**：系統必須在現有後台提供加班更正修改頁
```

# Rule 2 - 只有真正跨故事的限制才進全域需求，仍用 FR-nnn

- Level: `MUST`
- `## 需求` 的全域功能需求，只放無法合理歸屬單一故事、或明確跨越多個故事的限制。
- 全域需求繼續用 `FR-nnn` 接著編，不要另開 `GR-001`。
- 若某條規則主要只支撐單一故事，應回到該故事的 `FR` 或邊界情況。

## Good Example

- 這個例子是好的，因為生效日分界同時約束 US1 輸入、US2 確認與 US3 月結。

```md
### 全域需求

#### 功能需求

- **FR-012**: 本次更正的生效日 MUST 同時作為員工時薪與客戶計薪方式的分界。
```

## Bad Example

- 這個例子是壞的，因為把單一故事的修改頁欄位需求提升成全域，還改用 GR。

```md
## 共通規則與全域約束

- **GR-001**：系統必須提供加班更正修改頁
```

# Rule 3 - 故事級時間與品質指標掛 NFR；不要把 NFR 誤寫成故事內 SC

- Level: `SHOULD`
- 故事專屬的時間、可用性或負向回饋指標，寫在該故事的 `**非功能需求（NFR）**:`，編號用全域唯一 `NFR-001`…。
- 套件級可量測成果才寫進 `## 成功標準` 的 `SC-001`…。
- 沒有專屬 NFR 的故事可省略該小節。

## Good Example

- 這個例子是好的，因為時間門檻在故事 NFR，成果門檻在套件 SC。

```md
**非功能需求（NFR）**:

- **NFR-001**: 80% 的後台使用者 MUST 能在第一次使用時，於 3 分鐘內完成修改頁輸入並進入預覽。

## 成功標準

- **SC-001**: 在驗收資料下，100% 能從既有明細進入修改頁並帶入預覽，且此時尚未永久生效。
```

## Bad Example

- 這個例子是壞的，因為把時間門檻寫成 `US1-SC1`，套件又沒有 `SC-001`。

```md
**成功標準**

- **US1-SC1**：80% 的後台使用者能在 3 分鐘內完成修改頁輸入
```
