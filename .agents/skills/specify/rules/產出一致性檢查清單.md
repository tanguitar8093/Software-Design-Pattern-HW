# Rule 1 - 輸出前必須檢查所有輸入語意是否都有落點

- Level: `MUST`
- 在交付最終 spec 前，必須逐一檢查每個語意片段是否已被映射到 User Story、全域 `FR`、待澄清項、關鍵實體或假設。
- 若有任何高影響語意片段沒有落點，應先修補，不得直接輸出。

## Good Example

- 這個例子是好的，因為它逐項核對了 overtime 的核心語意。

```md
- 現有後台提供修改頁 -> US1 / FR-001
- 預覽後再確認 -> US2 / FR-005
- 既有月結核對 -> US3 / FR-009
- 生效日分界 -> 全域 FR-012
```

## Bad Example

- 這個例子是壞的，因為它遺漏了跨故事限制的落點。

```md
- 現有後台提供修改頁 -> US1
- 預覽後再確認 -> US2
```

# Rule 2 - 必須檢查故事結構、GWT 與編號契約

- Level: `MUST`
- 每個 User Story 都必須具備：作為…我希望…敘述、優先級理由、獨立驗證方式、三行 GWT 驗收情境、至少一條 `FR-nnn`。
- `FR-nnn` / `NFR-nnn` / `SC-nnn` 必須全域唯一且連續遞增。
- `**Then**` 必須單獨成行並接條列；文件中不得出現一句連寫的 Given／When／Then，也不得出現 `US1-FR1`、`GR-001`、`假設 / 當 / 則`。

## Good Example

- 這個例子是好的，因為故事結構完整，編號與 GWT 都對齊完成態。

```md
### User Story 1 - 在現有後台更正加班資料與計薪方式 (Priority: P1)

**驗收情境**:

1. **Given** 使用者已進入修改頁
   **When** 使用者送出修改頁
   **Then**
   - 仍允許進入預覽

**功能需求（FR）**:

- **FR-001**: ...
```

## Bad Example

- 這個例子是壞的，因為編號與驗收格式都是舊契約。

```md
### 使用者故事 1 - 在現有後台更正加班資料與計薪方式（優先級：P1）

**驗收情境**

1. **假設** 使用者已進入修改頁，**當** 使用者送出，**則** 系統應允許進入預覽

- **US1-FR1**：...
```

# Rule 3 - 必須檢查表頭輸入欄，且不得把舊表頭加回來

- Level: `MUST`
- 交付前必須確認表頭使用 `功能分支`，以及 `**輸入**:` 底下有 `來源`、`原始需求`、`使用者澄清決策` 條列。
- 不得使用 `規格名稱`、`**輸入需求**：`，不得把 ticket 全文糊成 `**輸入**:` 後面同一長行。
- `來源` 只是輸入欄子項，不得另開頂層「來源」區塊取代輸入。
- 新建功能不要寫 `## 規格改動`。

## Good Example

- 這個例子是好的，因為表頭與輸入欄都和活產物同構。

```md
**功能分支**: `001-overtime-correction`

**輸入**:

- 來源：`tickets/REDMINE-5825.md`
- 原始需求：
  - 現有後台需提供加班資料與計薪方式修改頁
- 使用者澄清決策：
  1. 預覽只顯示目前這筆加班前後差異
```

## Bad Example

- 這個例子是壞的，因為舊表頭與單行輸入都回來了。

```md
**規格名稱**：`001-overtime-correction`
**輸入需求**：Redmine #5825｜……整段需求糊在同一行……

## 規格改動

- 無（本規格為新建）
```

# Rule 4 - 全域需求、待澄清項與 placeholder 位置都必須正確

- Level: `SHOULD`
- 交付前應確認跨故事限制放在 `## 需求` 的全域 `FR`，待澄清項沒有濫用，且最終內容不殘留 `{{PLACEHOLDER}}`。
- 若輸出要作為可驗證成品，應再用 validator 做一次靜態檢查。

## Good Example

- 這個例子是好的，因為全域限制用 `FR-nnn`，且沒有殘留骨架。

```md
### 全域需求

#### 功能需求

- **FR-013**: 本功能不得新增帳號、角色或權限控管。
```

## Bad Example

- 這個例子是壞的，因為它保留了 placeholder，且把待澄清寫得太抽象。

```md
- **FR-002**: 系統 MUST 依據 [NEEDS CLARIFICATION: 還沒決定] 來調整時薪
- **NFR-001**: {{USER_STORY_NFR_001}}
```
