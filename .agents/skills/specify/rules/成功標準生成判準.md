# Rule 1 - 故事級品質指標寫成 NFR；套件級成果寫成 SC

- Level: `MUST`
- 每個有時間、可用性或負向回饋門檻的 User Story，至少要有一條掛在該故事下的 `NFR-nnn`。
- 整份功能的可量測成果必須寫在 `## 成功標準` 的 `SC-001`…，不可把套件成果只留在故事裡。
- 不可再使用 `USn-SCm`。

## Good Example

- 這個例子是好的，因為故事品質與套件成果分開，編號也對得上水球。

```md
**非功能需求（NFR）**:

- **NFR-003**: 90% 的使用者 MUST 能在不閱讀說明的情況下，完成一次預覽確認或中止不保存。

## 成功標準

- **SC-002**: 預覽頁 100% 只顯示目前這筆加班的修改前／後差異。
```

## Bad Example

- 這個例子是壞的，因為成功標準全寫成故事內 `US2-SC1`，套件沒有 `SC-nnn`。

```md
**成功標準**

- **US2-SC1**：90% 的使用者能完成一次預覽確認
```

# Rule 2 - 成功標準與 NFR 必須可量測，並依故事類型套用穩定模板

- Level: `MUST`
- 核心任務型故事，優先使用「`80%` 的使用者能在 `3 分鐘` 內完成第一次核心任務」。
- 瀏覽定位型故事，優先使用「使用者能在 `10 秒` 內找到目標內容」。
- 直接操作型故事，優先使用「`90%` 的使用者能在不閱讀說明下完成操作」。
- 套件級 `SC-nnn` 用可驗證百分比或明確通過條件，例如驗收資料下 `100%` 能完成主路徑。
- 若 prompt 未提供更強數據，優先採用上述預設值，不可任意漂移數字。

## Good Example

- 這個例子是好的，因為數值可驗證，且對應故事類型。

```md
- **NFR-001**: 80% 的後台使用者 MUST 能在第一次使用時，於 3 分鐘內完成修改頁輸入並進入預覽。
- **NFR-005**: 使用者在更正確認後，MUST 能在 10 秒內於既有月結報表找到目標月份結果。
- **SC-001**: 在遠峰零售 A02301／2026-08-08 驗收資料下，100% 能進入修改頁並帶入預覽。
```

## Bad Example

- 這個例子是壞的，因為數值隨意，且沒有對應故事類型。

```md
- **NFR-001**: 53% 的使用者能在 17 分鐘內完成更正
- **SC-001**: 系統大概很好用
```

# Rule 3 - 可用性痛點的負向回饋指標只在有明確風險時補充

- Level: `SHOULD`
- 只有當故事存在「找不到入口、誤以為已生效、看不到差異」這類明確痛點時，才補一條負向回饋 `NFR`。
- 負向指標應寫測試期間相關回饋低於 `10%`，不要憑空發明其他百分比。

## Good Example

- 這個例子是好的，因為它對應「找不到更正入口」的真實風險。

```md
- **NFR-002**: 與「找不到加班／計薪更正入口或無法調整必要欄位」相關的回饋，在測試期間 MUST 低於 10%。
```

## Bad Example

- 這個例子是壞的，因為沒有對應痛點，卻硬加一條回饋指標。

```md
- **NFR-009**: 任何客服抱怨都必須低於 2%
```
