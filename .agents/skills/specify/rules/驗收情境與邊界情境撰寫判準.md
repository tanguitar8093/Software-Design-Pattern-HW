# Rule 1 - 每個 User Story 都必須至少有一個直接對應核心需求的驗收情境

- Level: `MUST`
- 每個 User Story 至少要有一個驗收情境，且該情境必須直接驗證此故事最核心的 `FR`。
- 驗收情境應以實際可觀察的操作與結果撰寫，不可只重述需求標題。
- 若故事包含多個高重要度 `FR`，可增加多個情境，但仍應由同一個使用者價值串起。

## Good Example

- 這個例子是好的，因為情境直接對應「進入修改頁並帶入預覽」。

```md
1. **Given** 後台使用者正在查看遠峰零售員工 A02301 於 2026-08-08 的薪資明細
   **When** 使用者進入更正修改頁並調整加班結束
   **Then**
   - 接受這些輸入並可帶入預覽
```

## Bad Example

- 這個例子是壞的，因為它只是把故事名換句話說，沒有可驗證操作。

```md
1. **Given** 使用者想更正加班
   **When** 使用者更正加班
   **Then**
   - 系統應該支援更正加班
```

# Rule 2 - 驗收情境必須三行 GWT，Then 單獨成行後接條列

- Level: `MUST`
- 每個驗收情境都必須使用 `**Given**` / `**When**` / `**Then**`，條件、動作與結果分開。
- `**Given**`、`**When**`、`**Then**` 固定在行首；`**Then**` 必須單獨成行，結果用 `-` 條列，即使只有一條結果。
- 值若是多個欄位，在 `**When**` 或 `**Then**` 底下再條列。
- 禁止寫成一句 `**Given** …，**When** …，**Then** …`，也禁止 `**Then** 系統應……，且……` 連寫。
- 禁止改回 `假設 / 當 / 則`。

## Good Example

- 這個例子是好的，因為關鍵字分行，Then 是結果條列而不是一句話。

```md
1. **Given** 使用者已進入某筆加班的更正修改頁
   **When** 使用者選擇未滿單位處理為向下捨去、四捨五入或直接進位其中一種
   **Then**
   - 允許該選擇作為本次更正輸入的一部分
```

## Bad Example

- 這個例子是壞的，因為三個關鍵字擠在同一句，Then 也沒有條列。

```md
1. **Given** 使用者已進入修改頁，**When** 使用者選擇未滿單位處理，**Then** 系統應允許該選擇作為本次更正輸入的一部分
```

# Rule 3 - 邊界情況放在故事區塊之後的共用清單，不強制每個故事自帶邊界

- Level: `SHOULD`
- 可獨立驗證的例外應升成 GWT 驗收情境。
- 其餘局部例外、空狀態或範圍外禁止，寫在故事結束後的 `### 邊界情況`。
- 不要再寫故事內 `**邊界情境**`，也不要另開 `全域邊界情境`。

## Good Example

- 這個例子是好的，因為邊界集中在故事之後，且不重複故事已用 GWT 驗證的路徑。

```md
### 邊界情況

- 當修改前與修改後某欄位數值相同時，預覽仍應可理解地呈現該欄位狀態，不得因此無法進入確認。
```

## Bad Example

- 這個例子是壞的，因為每個故事又各寫一組邊界，且把已升成 GWT 的內容再抄一次。

```md
**邊界情境**

- 當使用者只改加班時間、未改計薪方式時，系統仍應允許進入預覽
```
