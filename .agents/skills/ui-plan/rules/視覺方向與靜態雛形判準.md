# Rule 1 - 先定稿 ui-plan.md，再依計畫產出靜態雛形

- Level: `MUST`
- 產出順序必須是先寫完 `system-analyze/ui-plan.md`，再依「雛形輸出規劃」與各頁「對應雛形檔案」產出 `system-analyze/ui/*.html` 與共用 CSS。
- 不可先畫 HTML 再倒推頁面邊界、操作流程或畫面文案。

## Good Example

- 這個例子是好的，因為控制平面先於可點雛形。

```text
1. 寫入 system-analyze/ui-plan.md
2. 再寫 system-analyze/ui/index.html、ui/album.html、ui/app.css
```

## Bad Example

- 這個例子是壞的，因為先做 HTML 再補計畫。

```text
1. 先隨手做三個 HTML
2. 再回頭寫 ui-plan.md
```

# Rule 2 - 雛形必須看起來像產品，且入口是產品主頁

- Level: `MUST`
- `ui/*.html` 只放使用者會看到的產品文案、假資料與操作；不可寫分析備註、US 編號、元件樹或 TODO。
- 多頁時固定以 `ui/index.html` 作為產品入口，不是 sitemap 或說明頁。
- 真實產品會換頁的才拆成新 HTML；空狀態、載入失敗、Modal、415 等留在同頁切換。

## Good Example

- 這個例子是好的，因為入口就是主頁，錯誤狀態不另開說明頁。

```html
<title>相簿</title>
<h1>相簿</h1>
<button type="button">建立相簿</button>
```

## Bad Example

- 這個例子是壞的，因為入口是檔案清單，畫面在講解計畫。

```html
<h1>畫面一：主頁</h1>
<p>這一頁對應 US-2，之後會接 API。</p>
<p><a href="album.html">相簿詳情</a></p>
```

# Rule 3 - 雛形必須覆蓋主流程，並用假資料模擬可操作互動

- Level: `MUST`
- HTML 雛形至少覆蓋主流程入口、關鍵中間狀態與主要結果；可用假資料、同頁切換與簡單腳本模擬表單、拖放、換頁。
- 假資料應對齊 `spec.md` 驗收例子與 `api-plan.md` 範例（名稱、日期分組、張數）。
- 狀態表中的畫面文案必須出現在 HTML 原始碼（含預設畫面或文件化的 query 切換）。

## Good Example

- 這個例子是好的，因為 reviewer 能從主頁走到相簿，並看到空狀態原文。

```text
ui/index.html → 日期分組的旅行／家庭／工作
ui/album.html?name=家庭 → 「這個相簿還沒有照片」
```

## Bad Example

- 這個例子是壞的，因為只有一張靜態圖，無法操作流程。

```html
<img src="home.png" alt="主頁截圖" />
```

# Rule 4 - 必須有雛形輸出規劃，query 切換不寫進產品畫面

- Level: `MUST`
- `ui-plan.md` 必須有 `## 雛形輸出規劃`：入口策略、預計檔案、換頁原則、假資料、互動原則、Review 目標。
- 非正式產品 URL（例如 `?empty=1`、`?error=unsupported`）只寫在本節，不寫進 HTML 畫面當說明文字。
- CSS 與版面應跟隨「視覺方向」，不可套用與產品氣質無關的通用電商／後台模板皮。

## Good Example

- 這個例子是好的，因為規劃寫清檔案與狀態切換，畫面本身仍是產品。

```md
## 雛形輸出規劃
- 多頁入口：`ui/index.html` 就是產品主頁
- `ui/index.html?empty=1`：`home-empty`
```

## Bad Example

- 這個例子是壞的，因為把 query 說明做成畫面上的 sitemap。

```html
<p>請加 ?empty=1 看空狀態（這是給 reviewer 的說明）</p>
```
