# Rule 1 - 先偵測既有測試套件再決定是否詢問

- Level: `MUST`
- 本期有前端時，先讀取既有 `package.json`、測試設定與測試目錄，確認是否已有瀏覽器端對端測試套件及其實際能力。
- 已有單一成熟且足以覆蓋本期關鍵瀏覽器互動的套件時，直接沿用並寫入技術研究與 plan，不呼叫 `/clarify`。
- 只有新專案尚未選定、既有套件無法覆蓋本期關鍵互動，或同時存在多套可行框架但沒有明確主框架時，才呼叫 `/clarify`。

## Good Example

- 這個例子先根據現有專案狀態決定，不重複詢問已成立的選型。

```text
package.json 已有 @playwright/test，且現有測試會啟動真瀏覽器
→ 直接沿用 Playwright，寫入 technical-research.md 與 plan.md
```

## Bad Example

- 這個例子忽略既有成熟套件，讓使用者重做沒有必要的選擇。

```text
專案已有 Cypress 且足以覆蓋需求
→ 仍固定詢問要不要改用 Playwright
```

# Rule 2 - 新 Web 專案未指定偏好時推薦 Playwright

- Level: `SHOULD`
- 新建 Web 專案尚未選定套件，且使用者未指定偏好時，瀏覽器端對端測試推薦 Playwright。
- 推薦理由必須對齊本期需要的真實 DOM、檔案選擇、拖放、非同步畫面、重新整理與 API 攔截能力，並說明瀏覽器安裝與執行時間成本。
- Playwright 不是所有前端的無條件預設；非 Web 前端、沒有瀏覽器互動，或已有單一成熟且足夠的套件時，不得強制替換。

## Good Example

- 這個例子把推薦限定在新 Web 專案並交代取捨。

```text
新建 Vite Web 專案，需驗證拖放、上傳、重新整理與真後端畫面
→ 推薦 Playwright，並說明首次需安裝瀏覽器及測試較慢
```

## Bad Example

- 這個例子把推薦誤寫成跨平台強制規定。

```text
任何前端一律移除既有套件並改用 Playwright
```

# Rule 3 - 前端瀏覽器測試的主證據必須來自執行期畫面打真後端

- Level: `MUST`
- 前端切片必須以真瀏覽器開啟執行期前端，透過使用者可操作的公開介面驅動並從執行期 DOM 或瀏覽器可見結果觀測。
- Vitest、Jest、Testing Library 等可以補純函式、元件或狀態邏輯，但不能取代本流程的前端瀏覽器端對端證據。
- 前端測試必須打真後端。不可在 API 邊界依契約做前端 Mock 當主證據，也不可再分成「前端 Mock 階段」與「完全端對端停用 Mock」。

## Good Example

- 這個例子是好的，因為前端瀏覽器測試直接打真後端。

```text
前端切片：Playwright → 執行期頁面 → 真 API → 真後端
```

## Bad Example

- 這個例子只驗證元件或靜態雛形，沒有證明執行期使用者行為。

```text
只跑 jsdom 元件測試，或直接讀 system-analyze/ui/index.html
→ 宣稱前端端對端完成
```
