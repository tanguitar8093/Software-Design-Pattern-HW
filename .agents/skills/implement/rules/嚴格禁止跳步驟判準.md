# Rule 1 - 預設一輪只推進恰好一個非切片 task，或恰好一個切片剩餘鏈

- Level: `MUST`
- 每一輪執行的任務集預設必須恰好是：1 個已解鎖且未完成的非切片 task，或同一 `[SLICE <CASE_ID>]` 尚未勾選的 TDD 鏈。
- 只有當多個 task 都明示 `[P]`、彼此無前後依賴、前置條件一致，且通過 `平行執行與檔案衝突判準` 時，才可把任務集擴大為同輪平行批次。不同切片即使都標 `[P]`，本輪仍只開一個 tdd Task。
- 未標 `[P]` 的不同切片或非切片序列 task，即使都已解鎖，也不得併成同一輪實作。
- 「續跑」只代表完成當前任務集的驗證與回寫後，再重算下一個 task；不代表本輪可一次吞掉多個切片。

## Good Example

- 這個例子是好的，因為同切片的 RGR 算同一任務集，下一切片不併入。

```md
目前已解鎖：`T026 [SLICE FE-E2E-001C] [TDD-RED]`，後面還有 T027 GREEN、T028 REFACTOR，以及 T029 另一切片。
本輪任務集 = {T026, T027, T028}。
開 1 個 tdd 子代理跑完後回寫三則，才重算 T029。
```

## Bad Example

- 這個例子是壞的，因為把不同切片一次打包，或把同切片拆成三次委派當唯一合法路徑。

```md
把 FE-E2E-001C 與 FE-E2E-001D 一次做完。
或堅持 T026、T027、T028 必須開三個子代理才算沒跳步。
```

# Rule 2 - 下列行為一律視為跳步驟，嚴格禁止

- Level: `MUST`
- 執行 `/implement` 時，下列行為一律視為跳步驟，必須立即停止並改回正確粒度：
  1. **跳過前置**：略過仍未完成或仍被 `Dependencies`／phase 阻塞的 task，直接做後面的 task。
  2. **合併不同切片或非切片序列**：把不同 `CASE_ID`、或未標 `[P]` 的非切片 task，併成同一輪實作或同一批回寫。同一 `[SLICE <CASE_ID>]` 的剩餘 TDD 鏈不算合併違規。
  3. **跨切片／跳過切片內順序**：一個 tdd 子代理做兩個以上 `CASE_ID`；或同切片內跳過 RED／ALIGN 直接改產品、跳過 GREEN 直接重構。同切片依序跑完 RGR（或 ALIGN 鏈）是要求，不是違規。
  4. **預做後續交付**：執行當前任務集時，順手寫入其他切片才該交付的測試、實作、重構、UI 或整合內容。
  5. **未完成閘門就續跑**：當前任務集尚未完成對應驗證，或尚未回寫 `[X]`，就開始修改下一個 task／切片的檔案或載入其 `Must Read` 作為執行依據。
  6. **提前／批次打勾**：尚未驗證完成就改 `[X]`，或一次把尚未各自有證據的 task（含其他切片）一起打勾。
  7. **越界吞責任**：在 Setup／Foundational／單切片中，偷做後續故事功能、整合責任或其他切片的完成條件。
- 若為了「比較快」「上下文已熟悉」「後面反正也要做」而觸發以上任一項，仍屬違規，不得合理化。

## Good Example

- 這個例子是好的，因為同切片依序做完，下一切片不動。

```md
FE-E2E-001C 子代理：先寫測並看到正確紅燈，再最小實作轉綠，再決定有無重構。
不預開 FE-E2E-001D 的測檔。
```

## Bad Example

- 這個例子是壞的，因為用效率理由把下一切片也做完，或跳過紅燈。

```md
反正 RED 很簡單，先改產品再補測。
同時先把下一 slice 的測試骨架也鋪好。
```

# Rule 3 - `[TDD-*]` 必須以切片為單位委派一個 Task 子代理

- Level: `MUST`
- 若當前已解鎖 task 含 `[TDD-RED]`、`[TDD-ALIGN]`、`[TDD-GREEN]` 或 `[TDD-REFACTOR]`，本輪只能開一個 Task 子代理，載入 `/tdd` 執行該 `CASE_ID` 的 `remaining_steps`。
- 委派時必須明示：`CASE_ID`、有序 `remaining_steps`、對應 `testplan.md` case。子代理內部必須先測、再最小實作、再整理，不得跳過清單中的步驟。
- 父代理不得自己寫該切片測檔或業務碼來代替子代理。
- `RED`／`ALIGN` 必須先 mapping 合格（缺口紅燈或已綠覆蓋率）才能進 GREEN；不得為了變紅改壞已正確產品。
- `GREEN` 只做讓當前缺口轉綠的最小實作；已綠則明示無實作。不得偷做下一個 case。
- `REFACTOR` 只在綠燈下做 behavior-preserving cleanup；不得夾帶新行為，也不得空勾。

## Good Example

- 這個例子是好的，因為一個切片只開一次 `/tdd` 子代理。

```md
當前：`T026 [US1] [SLICE FE-E2E-001C] [TDD-RED]`
開 1 個 Task 載入 tdd/SKILL.md：CASE_ID=`FE-E2E-001C`，remaining_steps=`RED,GREEN,REFACTOR`。
回傳三段證據後回寫 T026–T028。
```

## Bad Example

- 這個例子是壞的，因為一則一步開三次，或父代理自己把三步做完。

```md
T026 只派 RED；勾完再開 T027。
或父代理讀完 tdd rules 後自己把三步做完。
```

# Rule 4 - 當前 task 邊界外的交付物一律不得預做

- Level: `MUST`
- 本輪只允許修改與驗證「當前任務集」完成條件所必需的檔案與內容。
- 不得因為共用模組方便，就提前實作後續 task 才需要的行為、測試案例、抽象層或整合接線。
- 若實作當前 task 時發現後續 task 會受影響，最多只能留下最小必要的暫時邊界或 TODO 說明；不得直接把後續 task 做完並提前打勾。
- Setup／Foundational task 只能建立入口、fixture、helper 或共同依賴骨架，不得偷做某個故事 slice 的完整功能。

## Good Example

- 這個例子是好的，因為共用骨架停在當前 task 邊界內。

```md
當前 task：`T003` 建立技能欄位 schema 骨架。
agent 只加欄位／model 增量，不實作 change-answer 或 triple-guess 行為。
```

## Bad Example

- 這個例子是壞的，因為借 Foundational 之名預做後續故事功能。

```md
做 `T003` schema 骨架時，順便把 change-answer API、規則與前端按鈕全部做完。
理由是「後面一定用得到」。
```

# Rule 5 - 必須先驗證並回寫，才可重算下一個 task

- Level: `MUST`
- 當前任務集中的每一則（含切片鏈的各格）都必須先有對應驗證，再回寫該則 `[X]`。同一切片鏈可在分段證據齊全後一次回寫多則。
- 只有在當前任務集的回寫完成後，才可返回選任務流程，重新計算下一個已解鎖 task。
- 回寫完成前，禁止開始下一個 task 的實作、禁止把下一個 task 的 `Must Read` 當成當前執行依據、禁止預改其交付檔案。
- 合法平行批次仍須各自驗證後再各自回寫；不得只驗證其中一個就整批打勾。

## Good Example

- 這個例子是好的，因為續跑閘門完整且不可壓縮。

```md
1. 完成 FE-E2E-001C 子代理（RED／GREEN／REFACTOR）
2. 對三段證據驗證
3. 回寫 T026–T028 為 `[X]`
4. 重新讀取 `tasks.md`，才開始下一已解鎖切片或 Gate
```

## Bad Example

- 這個例子是壞的，因為把驗證／回寫與下一步實作壓縮成同一動作。

```md
agent 邊寫 `T007` 邊說 `T006` 大概沒問題，之後再補測試與打勾。
```
