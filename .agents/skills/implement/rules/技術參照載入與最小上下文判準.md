# Rule 1 - 實作前必須讀完當前 task 的 `Must Read` 指定部位

- Level: `MUST`
- 開始實作任一 task 前，必須先讀取該 task `Must Read` 列出的文件與具體部位。
- `Must Read` 的要求是精確載入，不得只讀同檔其他位置就視為已滿足參照。
- 若同一輪包含多個 task，必須分別確認每個 task 的 `Must Read` 是否都已覆蓋。

## Good Example

- 這個例子是好的，因為它先讀 task 指定的精確部位，再開始寫碼。

```md
agent 要做 `T010`。
它先讀 `contracts/openapi.yaml` 指定的 path 與 schema，再讀 `spec.md` 的驗收情境，確認事件 shape 與廣播語意後才實作。
```

## Bad Example

- 這個例子是壞的，因為它只看了 `tasks.md` 的一句描述，就直接憑印象開始實作。

```md
agent 要做 `T010`。
它沒有讀 `Must Read`，只因為知道這是 join room 流程，就直接自定義 event payload 與錯誤欄位。
```

# Rule 2 - `Optional` 與其他 artifacts 只在需要時才補讀

- Level: `MUST`
- `Optional` 只在需要補足鄰近上下文、視覺細節、共享檔案約束、驗證方式或局部決策依據時才讀。
- 不得把 `tasks.md`、`plan.md`、`research.md`、`contracts/`、`data/`、`ui/` 全部預先全文載入後再開始動作。
- 若已能依 `Must Read` 與現有程式碼收斂方案，就不應額外擴張上下文。

## Good Example

- 這個例子是好的，因為它先靠 `Must Read` 完成主要判斷，只在需要視覺細節時才補讀 `Optional`。

```md
agent 要做大廳頁的 UI task。
它先讀 `ui/ui-plan.md` 指定段落與 contract schema，只有在需要對齊靜態稿排版時才補讀 `ui/room-lobby.html`。
```

## Bad Example

- 這個例子是壞的，因為它把所有 artifacts 一次載入，造成上下文膨脹卻沒有提升當前 task 的決策品質。

```md
agent 準備做 `T011`。
它先把 `spec.md`、`plan.md`、`research.md`、`techstack.md`、`contracts/openapi.yaml`、`data-model.dbml`、所有 `ui/*.html` 全讀一遍，之後才開始判斷四碼輸入框。
```

# Rule 3 - 只有在共享修改面或整合風險存在時才補讀相鄰 task

- Level: `SHOULD`
- 若當前 task 會修改與前後 task 共用的檔案、共用狀態模型或共用驗證面，應補讀相鄰 task 的描述與參照，避免局部正確、整體失配。
- 若當前 task 是獨立且邊界清楚的單點任務，則不必為了形式完整而額外補讀相鄰 task。

## Good Example

- 這個例子是好的，因為它只在真的共享修改面時才往前後 task 延伸閱讀。

```md
agent 要做 `frontend/src/main.js` 的跨端整合 task。
由於同檔前面已被其他 task 使用，agent 補讀相鄰 task，確認 page flow 與 app state 不會互相覆寫。
```

## Bad Example

- 這個例子是壞的，因為它把「補讀相鄰 task」誤變成每次都要整段通讀整個 story。

```md
agent 要做一個只改 `backend/.env.example` 的 setup task。
它仍然把整個 `US3` 區塊全部補讀一遍，卻沒有任何共享檔案或整合需求。
```
