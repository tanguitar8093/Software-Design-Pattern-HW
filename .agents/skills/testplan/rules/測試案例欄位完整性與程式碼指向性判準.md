# Rule 1 - 每個 TDD 切片都必須具備可交接到測試程式碼的核心欄位

- Level: `MUST`
- 每個 TDD 切片至少必須包含：`對應需求`、`唯一測試意圖`、`受測部位`、`前置資料（Arrange Fixture）`、`操作（Act）輸入`、`觀測通道／預期輸出`、`必須維持不變`、`預期 RED 原因`、`本案例不驗證`。
- 驗收旅程雖可不如切片細，但仍應至少具備：`組成切片（Slice）`、`前置資料（Arrange Fixture）`、`操作（Act）輸入`、`觀測通道／預期輸出` 與 `本案例不驗證`。
- 不可把 `觀測通道` 與 `預期輸出` 拆成兩欄，也不可把 `操作（Act）輸入` 寫回 `前置資料（Arrange Fixture）`。

## Good Example

- 這個例子是好的，因為它已足以讓後續 session 直接落成測試而不需猜測邊界。

````md
### BE-API-001A - 送出遠峰範例更正並取得預覽

- **唯一測試意圖**: 依遠峰範例送出預覽後，正式 API 回傳本筆 before／after，且正式加班尚未被永久變更。
- **受測部位**:
  - `POST /payrolls/{id}/correction/preview`
- **前置資料（Arrange Fixture）**: FX-FARFENG-AUG08
- **操作（Act）輸入**:
  - 加班結束 `19:50`
  - 送出預覽
- **觀測通道／預期輸出**:
  - 預覽 API 回應 → 含本筆修改前／後差異
````

## Bad Example

- 這個例子是壞的，因為它只留下模糊方向，或把 Then 拆回兩欄。

````md
### BE-API-001A - 預覽流程

- 測一下預覽應該可以成功
- **觀測通道**: 預覽 API
- **預期輸出**: 有差異
````

# Rule 2 - 受測部位必須直接指出 public seam

- Level: `MUST`
- `受測部位` 必須能讓後續 `/implement` 直接知道要從哪條 public seam 進入，例如具體 HTTP 端點或具體畫面操作區。
- 後端切片指向正式 API；前端切片指向 Playwright 真頁面。不可只寫「後端 API」「前端頁面」。
- 不可把 Model／Repository internals 當受測部位。若案例需要多個 public seam，應先檢查是否太厚；只有驗收旅程才可列出多個 seam。

## Good Example

- 這個例子是好的，因為它直接點出正式入口。

````md
- **受測部位**:
  - `POST /payrolls/{id}/correction/preview`
- **受測部位**:
  - 畫面：明細 → 修改頁 → 預覽頁（Playwright）
````

## Bad Example

- 這個例子是壞的，因為後續實作者還要再猜一次入口。

````md
- **受測部位**: 後端 API
- **受測部位**: 前端頁面
- **受測部位**: OvertimeRepository
````

# Rule 3 - 觀測必須回到正式介面，且與預期寫在同一欄

- Level: `MUST`
- `觀測通道／預期輸出` 每一條寫成 `在哪裡看 → 應看到什麼`。
- 應優先寫正式讀取方式：API 回應、正式 GET、使用者可見畫面。不可直接偷看 side channel 或 ORM 內部欄位。
- `必須維持不變` 要清楚指出失敗時哪些狀態不能前進。

## Good Example

- 這個例子是好的，因為通道與預期成對，且用正式介面觀測。

````md
- **觀測通道／預期輸出**:
  - 預覽 API 回應 → 含本筆修改前／後差異
  - 再次讀取更正表單現值 API → GET 仍顯示加班結束 19:25
- **必須維持不變**: 預覽成功後正式加班結束時間仍為 19:25
````

## Bad Example

- 這個例子是壞的，因為它鼓勵旁路驗證，或把 Then 拆成兩欄。

````md
- **觀測通道**: 直接看資料表欄位
- **預期輸出**: 應該有改到
````

# Rule 4 - User Story 標頭的 FR / NFR 應引用 spec，而不是重寫需求內容

- Level: `SHOULD`
- `testplan.md` 在 User Story 標頭只保留 `對應 FR`、`對應 NFR`，以 `spec.md` 章節引用為主。
- 不應把同一條 FR / NFR 內容再用相近 wording 重寫一次。
- 真正新增的測試資訊，應寫在旅程／切片的 `受測部位`、`操作（Act）輸入`、`觀測通道／預期輸出`、`必須維持不變` 與 `預期 RED 原因` 中。

## Good Example

- 這個例子是好的，因為故事標頭只保留引用。

````md
**對應 FR**:
- `spec.md` -> `User Story 1 > FR-001`

**對應 NFR**:
- `spec.md` -> `User Story 1 > NFR-001`
````

## Bad Example

- 這個例子是壞的，因為它在 testplan 中再寫一遍需求本體。

````md
**對應 FR**:
- `FR-001`: 使用者 MUST 能從既有加班薪資明細進入更正頁並調整該筆加班。
````
