# Rule 1 - 必須先打開現行測檔，再決定 Keep／Modify／Delete／Add

- Level: `MUST`
- 展開工單前，必須把 `testplan.md` 的目標案例對上 `tests/phpunit/` 與 `tests/e2e/` 的現行測檔。不可只看 testplan 就預設每個切片都是新增一組 `[TDD-RED]`。
- 比較結果只能是四種動作之一：Delete、Modify、Add、Keep。落點能從現行測檔對出來就自己判；對不上才停下來問人。
- 不可把 Keep／Modify／Delete／Add 寫進 spec 或 testplan，也不可要求 testplan 先標測檔路徑。

## Good Example

- 這個例子是好的，因為先對到現行月結測，才決定哪些走 ALIGN、哪些不開工單。

```text
testplan BE-API-001A 寫「查詢含小計」
現行 `BeApi003AMonthlyReflectsConfirmedTest.php` 已測同一查詢但沒有小計
→ Modify，開 `[TDD-ALIGN]`
```

## Bad Example

- 這個例子是壞的，因為沒打開現行測檔，就把每則切片編成 RED。

```text
testplan 有 BE-API-001A
→ 直接新增 `BeApi001ASubtotalTest.php` 的 `[TDD-RED]`
```

# Rule 2 - Delete 只用於來源明文取消的行為；沒重列不是 Delete

- Level: `MUST`
- `[TDD-REMOVE]` 只用於票、spec 假設或 testplan「本輪不納入」**點名取消**的驗收或斷言。
- 本包 testplan 沒重列的舊案例，預設是 Keep，不是 Delete。更正流程測沒出現在本包 testplan，仍是 Keep。
- 不可因為案例 ID 重編、或舊測檔不在本包目錄名底下，就把現行測當成不存在。

## Good Example

- 這個例子是好的，因為 REMOVE 綁的是明文取消，不是「這包沒寫到」。

```md
- [ ] T005 [US1] [TDD-REMOVE] 刪除「重跑按鈕必須不存在」斷言
  - 原因（Why）: testplan「本輪不納入」明文取消，不是因為沒重列。
```

## Bad Example

- 這個例子是壞的，因為把沒重列的空月份測當成要刪。

```md
- [ ] T099 [US1] [TDD-REMOVE] 刪除 `BeApi003BEmptyMonthTest.php`
  - 原因（Why）: 本包 testplan 沒寫 003B
```

# Rule 3 - 一則切片只做一種動作；Keep 不開工單

- Level: `MUST`
- 同一個 testplan 切片不得同時 ALIGN 又 RED。同一測檔既要改舊斷言、又要加新案例：先 ALIGN 舊方法，再另開切片 RED。
- Keep：現行有測、本輪行為仍成立 → 不開工單、不複製新測試。
- Modify：同一案例預期變了 → `[TDD-ALIGN]` → `[TDD-GREEN]` → `[TDD-REFACTOR]`。
- Add：testplan 有、現行沒有對應測 → `[TDD-RED]` → `[TDD-GREEN]` → `[TDD-REFACTOR]`。RED 標題寫映射測試，不寫「先讓失敗」。產品已符合不改成 Keep。
- Delete：明文取消 → `[TDD-REMOVE]` → 刪碼 → `[REGRESSION]`。REMOVE 可不綁 testplan 切片 ID。

## Good Example

- 這個例子是好的，因為 Keep 的空月份沒有工單，Modify 與 Add 分開。

```text
BE-API-001A → ALIGN 鏈（改 `BeApi003A…`）
BE-API-001B → Keep，無工單
BE-API-001C → RED 鏈（新檔）
```

## Bad Example

- 這個例子是壞的，因為為 Keep 複製測，或把 Modify 做成另開 RED。

```text
BE-API-001B → 再寫一組 RED／GREEN／REFACTOR
BE-API-001A → 新增平行測檔 `[TDD-RED]`，舊檔不動
```

# Rule 4 - 既有測試影響只當文末備註，不是執行 Phase

- Level: `MUST`
- 給人看的對照放在 `## 備註：既有測試影響（給人看，implement 不依此執行）`，位於實作策略之前。
- 只要有 Keep 的 testplan 案例（有案例但無工單），備註必須點名那些案例 ID 與動作 `Keep`，讓人與 validator 知道不是漏寫。
- implement 依標題執行，不靠這張表。不可把盤點做成 Phase，也不可把標題文法寫成長契約塞進產物。

## Good Example

- 這個例子是好的，因為備註在文末，Keep 案例有列出來。

```md
## 備註：既有測試影響（給人看，implement 不依此執行）

| 現行測或目標案例 | 動作 | 依據 |
|---|---|---|
| `BE-API-001B`、`FE-E2E-001B` | Keep | 空月份沒變 |
```

## Bad Example

- 這個例子是壞的，因為把盤點當成執行 Phase，或漏列 Keep。

```md
## Phase 0: 既有測試影響盤點
implement 先讀這張表再決定做哪張工單。
```
