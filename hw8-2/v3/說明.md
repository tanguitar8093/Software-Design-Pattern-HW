### v3 重構總覽

v3 目標：把 v2（觀察者模式 + 狀態模式，服務於單一 Waterball 社群機器人）往上抽出一個**通用的有限狀態機模組 (FSM Module)**，再包一層 **Bot 模組 (Facade)** 給應用層使用。整個重構拆成 8 個步驟，每步只解決一個 Force，做完才進下一步。

依據：`hw8-2/README.md`「設計需求 - 1：FSM 模組設計」與「設計需求 - 2：Waterball 社群機器人模組設計」。

## 步驟 1：Guard（策略模式）

### Context（脈絡）

FSM 模組的 `Transition` 需要一個「條件判斷」機制：`from A, event=E, guard=G, to=B`——只有 `G` 成立時，轉移才會觸發。從 README 需求盤點，實際會出現的條件至少有：

- `king` 指令：只有管理員(Admin)才能用 + 額度 ≥ 5
- `record` 指令：額度 ≥ 3（無身分限制）
- `stop-recording`：只有錄音者(recorder)本人才能用
- 登入事件：在線人數 ≥ 10 才切到互動狀態
- 登出事件：在線人數 < 10 才切回預設對話狀態
- `king-stop`：只有管理員才能用
- `play again`：額度 ≥ 5

### Problem（困難點）

這些條件種類差異很大（身分/額度/人數/特定使用者），若直接寫成 if-else 塞進 `Transition` 或 `FiniteStateMachine` 內部，會導致：

1. FSM 模組被迫認識「額度」「管理員」「在線人數」這些屬於 Waterball 社群的業務概念。
2. 每多一種條件，就要去改 FSM 核心程式碼。

### Force（衝突的勁）

- **Force-通用性**：FSM 模組要維持「不知道任何業務邏輯」的純粹性。
- **Force-擴充性**：新增一種判斷條件時，不能修改 `Transition`/`FiniteStateMachine` 既有程式碼。
- **Force-組合性**：有些條件需要「同時滿足多個判斷」（例如 `king` 指令要「是管理員」且「額度足夠」）。

### 依據（README 原文）

> 「不過有限狀態機應該要是一個獨立的模組，FSM 模組並不知曉『社群機器人』這個概念，此模組唯一的職責範圍就是允許開發者輕鬆建立有限狀態機，並能注入開發者想要的行為至有限狀態機中。」

> 「此 FSM 模組在一定的限度下遵守 OCP，當 Client 在從事以下維護/開發行為時，無需修改 FSM 模組的既有程式碼：⋯擴充新的 Trigger、**Guard**、Action」

`Guard` 這個詞是題目原文用字，不是自創術語。

### Pattern：Strategy Pattern

把「判斷條件」抽成一個介面，讓 FSM 模組只認得這個介面，不認得具體邏輯：

```
interface Guard {
    +evaluate(context: TransitionContext) : bool
}
```

`Transition`（後續步驟才會建立）只依賴 `Guard` 這個介面，完全不用知道背後在檢查額度、身分、還是人數。

### 本次新增的類別（詳見 `OOA-Clean.mmd` 內 `[v3-STEP1]` 區塊）

- `TransitionContext`：Guard 評估時唯一能存取的資料快照（sourceId/role/quota/onlineCount/recorderId），FSM 與業務邏輯之間的橋樑，FSM 本身不需理解這些欄位的業務意義。
- `Guard`（介面）：`evaluate(context): bool`
- `RoleGuard`：檢查發起者角色（對應 `king`/`king-stop` 的管理員限制）
- `QuotaGuard`：檢查額度門檻（對應 `king`(5)/`record`(3)/`play again`(5)）
- `RecorderGuard`：檢查發起者是否為目前錄音者（對應 `stop-recording`）
- `ParticipantCountGuard` + `Comparator`(GTE/LT)：檢查在線人數門檻（對應登入/登出後的狀態切換條件）
- `AndGuard`：組合多個 Guard，全部成立才回傳 true（對應 `king` 指令「管理員 且 額度足夠」的複合條件）

### 本次刻意不做的事（留給後續步驟，避免一次改太多）

- 尚未建立 `Transition`/`FiniteStateMachine`，因此上述 Guard 目前是**獨立定義、尚未被接上任何轉移邏輯**的類別。
- `Bot`/`BotState` 仍完整沿用 v2 的做法（權限、額度判斷邏輯還留在原本的位置），**v2 該有的觀察者模式與狀態模式內容全部保留、沒有刪減**，只是額外插入 Guard 這組新類別，等後續步驟才會真正把 `BotState` 內部的權限/額度 if-else 改成呼叫 Guard。
- 額度「扣除」的動作（有副作用）刻意不放在 Guard 裡，Guard 只負責「唯讀判斷」，扣除額度會在步驟 2（Action / 命令模式）處理，維持 Guard「無副作用」的乾淨語意。

## 步驟 2：Action（命令模式）

### Context（脈絡）

FSM 需要在三種時機執行「有副作用」的行為：

1. 狀態的進場行為 (Entry Action)
2. 狀態的出場行為 (Exit Action)
3. 轉移本身的行為 (Transition Action)

從 README 盤點，實際會出現的副作用至少有：

- `king`/`record`/`play again` 指令觸發轉移時：扣除對應額度 (5/3/5)
- 進入知識王出題狀態時：回覆 `KnowledgeKing is started!` 並出第一題
- `play again` 指令：回覆 `KnowledgeKing is gonna start again!`
- 預設對話狀態/互動狀態收到貼文時：留言 `Nice post` 或 `How do you guys think about it?`
- 感謝參與狀態進場時：依是否有人廣播，選擇用聊天訊息或語音公布遊戲結果

### Problem（困難點）

這些副作用種類差異很大（扣額度/回聊天室訊息/留言/語音廣播），且同一個轉移可能需要「依序執行多個」副作用（例如某條轉移可能同時要扣額度又要回覆訊息）。若直接把這些操作寫成方法呼叫塞進 `Transition`/`FiniteStateMachine`/`State` 內部，會導致：

1. FSM 模組被迫認識「額度」「聊天室訊息」「廣播」這些屬於 Waterball 社群的具體操作。
2. 每多一種副作用，就要去改 FSM 核心程式碼。
3. 「依序執行多個副作用」這種需求，如果沒有組合機制，只能寫成一長串方法呼叫，無法被視為單一個「行為」重複使用。

### Force（衝突的勁）

- **Force-通用性**：FSM 模組要維持「不知道任何具體副作用內容」的純粹性（跟 Guard 面對的 Force 一致，但這次針對「動作」而非「條件」）。
- **Force-擴充性**：新增一種副作用時，不能修改 `Transition`/`State`/`FiniteStateMachine` 既有程式碼。
- **Force-可組合性**：Entry/Exit/Transition 三種時機都可能需要依序執行多個副作用，需要能把多個 Action 視為一個 Action 使用。

### 依據（README 原文）

> 「當機器人進入此狀態時，會先做『進場行為 (Entry Action)』；而當機器人離開此狀態時，則會做『出場行為 (Exit Action)』。」

> 「此 FSM 模組在一定的限度下遵守 OCP⋯擴充新的 Trigger、Guard、**Action**」

### Pattern：Command Pattern

把「要執行的副作用」抽成一個介面，讓 FSM 模組只認得這個介面，不認得具體內容：

```
interface Action {
    +execute(context: TransitionContext) : void
}
```

`State`/`Transition`（後續步驟才會真正接上）只依賴 `Action` 這個介面，完全不用知道背後是在扣額度、還是在發聊天訊息。

### 本次新增的類別（詳見 `OOA-Clean.mmd` 內 `[v3-STEP2]` 區塊）

- `TransitionContext` 新增 `receiver: Object` 欄位：這是 Command 模式裡「Receiver」的角色——一個不具型別的通用參考（實際指向 `Bot` 實例），具體 `Action` 實作會將其向下轉型後呼叫對應方法（如 `receiver.replyChatMessage()`），FSM 核心與 `Action` 介面本身都不需要知道 `receiver` 的實際型別。
- `Action`（介面）：`execute(context): void`
- `DeductQuotaAction`：扣除額度（對應 `king`/`record`/`play again` 的額度扣除）
- `ReplyChatMessageAction`：回覆聊天室固定訊息（對應知識王開始/再玩一次等提示訊息）
- `CommentOnPostAction`：在貼文下留言（對應 `Nice post`/`How do you guys think about it?`）
- `BroadcastVoiceAction`：語音廣播（對應感謝參與狀態的語音公布結果）
- `CompositeAction`：依序組合多個 Action（對應「同一次轉移需要依序執行多個副作用」的情境，設計手法跟步驟 1 的 `AndGuard` 對稱）

### 本次刻意不做的事（留給後續步驟）

- 尚未建立 `Transition`/`FiniteStateMachine`，`Action` 目前也還是**獨立定義、尚未被接上任何轉移或狀態生命週期**的類別。
- `Bot`/`BotState` 仍完整沿用 v2 的做法，v2 該有的內容全部保留、沒有刪減。
- `TransitionContext.receiver` 刻意用不具型別的 `Object` 表示，尚未決定要不要在後續步驟具體化成介面（例如 `ActionReceiver`），先維持最小改動。
