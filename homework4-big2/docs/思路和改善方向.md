# 思路過程

## OOA (Object-Oriented Analysis)

- **類別圖**: 按照規格描述畫出 Class 和 Class 之間的關聯。
- **流程圖**: 按照流程描述畫出遊戲的流程。
- **發現 Force (交集產生 Problems)**:
  1. **策略模式句型 (原始型)**: `bv`, `ocp` => 牌型有歸類和擴充的需求。
  2. **責任鍊模式句型 (比對型)**: `bv`, `ocp` => 系統需要自動選擇牌型的需求。
  3. **樣板方法**: 大部分重複，少部分變動 (留同存異) => 回合間的行為存在大部分相同、少部分差異，需要將行為分析和萃取。

## OOD (Object-Oriented Design)

按照設計模式的 Form 來處理 Forces 部分：

### 實現目標

1. **將 OOA 階段的 Card Pattern 拆成 Pattern Handler 和 Card Pattern**
   - **責任鍊模式 + 樣板方法**: Pattern Handler 處理自動選擇牌型的行為，解耦處理邏輯集中在主 code 的情況。
   - **策略模式 Card Pattern**: 封裝各牌型，萃取相同屬性行為，方便擴充，解耦所有牌型集中在主 code 的情況。
2. **將 Game 處理整個遊戲行為，拆成 Rounds 處理核心遊戲邏輯**
   - Game 只負責提供遊戲資料，以及從資料判斷遊戲階段 => 解耦遊戲核心邏輯。
   - **策略模式 + 樣板方法**: `RoundStrategy` 封裝第一回合和之後回合的不同行為，萃取共同行為。

## OOP (Object-Oriented Programming)

大部分建立 Class 算順利，但在解耦 `Game` 和 `Rounds` 遇到很多問題：

1. **循環依賴問題**:

   > 「發現我的設計方式是用 Rounds 去操控 Game 資料，所以會有循環依賴的問題」

   這邊嘗試用 `GameContext` 介面的方式，定義好開放給 Rounds 操作的 Game 屬性和方法，不暴露多餘的部分。然而，在使用樣板方法萃取時，發現初步的 OOD 分析太淺了。

2. **步驟細節難以歸類**:

   > 「我嘗試把每個步驟細節都找出來，按照步驟具體實作，發現很難按照需求歸類」

   實作上遇到第一回合與之後回合的 `play`、`pass` 行為處理困難：先發玩家和非先發玩家的出牌條件都不同，結束時的行為也不同。
   後來求助教練才發現，不能只分析一次，要多分析幾次行為。像我拆解出來的步驟，其實很多都是驗證行為，可以歸納為「驗證步驟」(過程可參考 ood1~ood2)。程式實作的步驟也發現不能總用線性思考處理問題，以下是整個思路的推進過程。

3. **初版問題**:
   按照直覺刻出初版，雖然架構比較亂，但也找出很多需求規格沒發現的問題。大部分是驗證問題，`pass`、`play` 在不同回合的組合不好歸納。

4. **重新分析樣板方法**:
   受困好幾天後，依照教練建議重看樣板方法影片，嘗試再次分析：

   #### 第一回合

   - 之後的第一回合先發，就算沒清空頂牌，先發玩家可以不用管頂牌 => 無視頂牌 **(同)**
   - 先發玩家可出任何牌型 **(異)**
   - 先發玩家不得 Pass **(同)**

   - 出牌成功玩家設為頂牌 **(同)**

## 教練的二次萃取與建議

### 第一回合：

```python
game.找出 current_player() # 梅花三
# 頂牌規則，在`驗證時`才要判斷，延後處理
# 梅花三規則，`驗證時`判斷
# 先發玩家不得 pass `驗證時`判斷
cards = current_player.出牌()
game.驗證(cards) # 驗證頂牌、驗證第一回合梅花三、驗證先發玩家不得 pass // 如果驗證沒過， loop 讓玩家出到過為止
game.更新遊戲資訊()
game.判斷遊戲是否結束()
```

### 之後回合：

```python
game.找出 current_player() # 透過頂牌更新遊戲資訊
cards = current_player.出牌()
game.驗證(cards) # 驗證頂牌、驗證第一回合梅花三、驗證先發玩家不得 pass // 如果驗證沒過， loop 讓玩家出到過為止
game.更新遊戲資訊()
game.判斷遊戲是否結束()
```

這時會發現只有兩個地方是 **(異)**：

1. 找出 `current_player`
2. 驗證時要判斷第一回合是梅花三

_(註：`current_player` 可以透過 init 時自動幫遊戲配置選好，這個邏輯在拆樣板方法前就預先處理了，感覺可以直接省去拆樣板方法的一部分心力。)_

**學到的教訓**：
讓我知道問題在哪——用 client 方式思考，直挺挺按照步驟走流程是不夠的，因為很難察覺問題。同時也對樣板方法有進一步認識：有些情況不能只分析一次，也不能只用線性思考，要從每次分析結果學會「再分析」和「再歸納」。

## 架構改善：GameContext 與 RoundResult 思路

針對 `GameContext`，教練提供了另一個建議：**可以把詳細資料都拆開來，不要都給 game 帶過去**，類似：

```python
class Round:
    def __init__(
        self,
        players: list[Player],
        rounds: int,
        top_play: CardPattern | None,
        top_player: Player | None,
        is_first_round: bool,
    ):
        ...
```

`Game` 只留最重要的參數。舉例來說，這邊是回合要運作需要的資料，而 `Game` 完全不需要知道這回合發生什麼事，只需要拿回 `top_play`, `top_card`, `is_game_over` 就能判斷遊戲進行與否。

**我的突發奇想 (Data In, Data Out)**：

> 開一個 `RoundResult` 類別，`Round` 每回合會 output `RoundResult`。
> 下一回合再從 `RoundResult` 拿來當 input 持續迭代更新，一直到遊戲結束。

但這個想法一開始沒有設計依據，先記錄下來，有機會再嘗試。實作需求中若發現需求有些地方是不合理，是非常合理的，工作也是這樣。

_可再參考：透過循序圖的方式來處理行為，當你碰到複雜行為時，你透過這樣的方式來拆分類別之間互動職責與行為 (function) 的封裝。_

## 最終實作：RoundResult 解析

後續實作了 `RoundResult` 功能，AI 分析結果如下：

### 為什麼這個架構比 Context/Protocol DI 更強？

1. **去耦合 (Decoupling)**
   把 `RoundStrategy` 中 `import GameContext` 移除了，這代表這套回合系統甚至可以被拿去別的卡牌遊戲直接套用，因為它只依賴單純的 Python 原生參數列。
2. **純粹性 (Functional Shell / Pure-ish Logic)**
   回合系統的邏輯變得更像「純函式」，給予特定的參數進去，就一定會吐出符合預期的 `RoundResult` 回來，不會偷偷改變外面的全域或者遊戲的私有變數，讓追蹤臭蟲極度容易 (如果下一回合開始玩家錯了，那一定是回傳的 `RoundResult` 有錯)。
3. **消除上帝物件 (No God Object)**
   一開始本來為了讓 Strategy 改狀態，要丟 `self` 進去，為了限制權限又弄出一個 `GameContext` (Facade)。直接換為回傳值設計，直接省略了這個層層防護，架構減輕 20% 開發負擔！
