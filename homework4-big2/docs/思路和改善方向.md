思路過程

OOA:
類別圖: 按照規格描述畫出 class 和 class 之間的關聯
流程圖: 按照流程描述畫出 遊戲的流程
發現 force 交集交集產生 problems:

1. 策略模式句型 (原始型): bv, ocp => 牌型有歸類和擴充的需求
2. 責任鍊模式句型 (比對型) bv, ocp => 系統需要自動選擇牌型的需求
3. 樣板方法: 大部分重複, 少部分變動 (留同存異) => 回合間的行為從在大部分相同, 少部分差異, 需要將行為分析和萃取

OOD:
按照設計模式的 Form 來處理 forces 部分,
實現:

1. 將 OOA 階段的 Card Pattern 拆成 Pattern handler 和 Card Pattern
   1. 責任鍊模式 + 樣板方法: Pattern handler 處理自動選擇牌型的行為, 解耦處理邏輯集中在主 code 的情況
   2. 策略模式 Card Pattern: 封裝各牌型, 萃取相同屬性行為,方便擴充, 解耦所有牌型集中在主 code 的情況
2. 將 Game 處理整個遊戲行為, 拆成 rounds 處理核心遊戲邏輯, game 只負責提供遊戲資料, 以及從資料判斷遊戲階段 => 解耦遊戲核心邏輯
   1. 策略模式 + 樣板方法: RoundStragety 封裝第一回合和之後回合的不同行為, 萃取共同行為

OOP:
大部分建立 class 算順利,
但在解耦 game 和 rounds 遇到很多問題

1. `發現我的設計方式是用 rounds 去操控 game 資料, 所以會有循環依賴的問題`,
   這邊是用 GameContext 介面的方式, 定義好開放給 rounds 操作的 game 屬性和方法, 不會暴露多餘的部分
   然後在嘗試萃取樣板方法, 發現初步 OOD 分析太淺了,
2. `我嘗試把每個步驟細節都找出來, 按照步驟具體實作, 發現很難按照需求歸類`
   實作上會遇到第一回合, 之後回合的 play, pass 行為處理, 先發玩家和不是先發玩家的出牌條件都不同, 結束時的行為也不同
   後來求助教練才發現, 不能只分析一次, 要多分析幾次行為, 像我拆解出來的步驟, 其實很多都是驗證行為, 可以歸納為驗證步驟 (過程可看 ood1~ood2)
   程式實作的步驟也發現不能總用線性思考處理問題, 以下是整個思路的推進過程

3. 按照直覺刻出初版, 雖然架構比較亂, 但也找出很多需求規格沒發現的問題, 大部分是驗證問題 pass, play 在不同回合的組合不好歸納
4. 受困好幾天, 依照教練建議, 重看樣板方法影片, 嘗試再次分析:

    先發玩家可出任何牌型  (異)

    出牌成功玩家設為頂牌 (同)

然後教練再次幫我萃取和建議:

第一回合：

```
    game.找出 current_player() # 梅花三
    # 頂牌規則，在`驗證時`才要判斷，延後處理
    # 梅花三規則，`驗證時`判斷
    # 先發玩家不得 pass `驗證時`判斷
    cards = current_player.出牌()
    game.驗證(cards) # 驗證頂牌、驗證第一回合梅花三、驗證先發玩家不得 pass // 如果驗證沒過， loop 讓玩家出到過為止
    game.更新遊戲資訊()
    game.判斷遊戲是否結束()
```

之後回合：

```
    game.找出 current_player() # 透過頂牌更新遊戲資訊
    cards = current_player.出牌()
    game.驗證(cards) # 驗證頂牌、驗證第一回合梅花三、驗證先發玩家不得 pass // 如果驗證沒過， loop 讓玩家出到過為止
    game.更新遊戲資訊()
    game.判斷遊戲是否結束()
```

這時會發現只有兩個地方是(異)
找出 current_player
驗證時要判斷第一回合是梅花三
current_player 可以透過 init 時自動幫遊戲配置選好
(init 時自動幫遊戲配置選好 這個邏輯再拆樣板方法前就預先處理了, 感覺可以直接省去拆樣板方法的一部分心力)

讓我知道問題在哪: 用 client 方式思考直挺挺按照步驟走流程是不夠的, 是很難察覺問題的
也對樣板方法有進一步認識, 有些情況不能只分析一次, 也不能只用線性思考, 要從每次分析結果學會再分析和歸納

針對 GameContext, 教練也有提供另一個建議是:
可以把詳細資料都拆開來, 不要都給 game 帶過去, 類似

```
    class Round:
    def **init**(
    self,
    players: list[Player],
    rounds: int,
    top_play: CardPattern | None,
    top_player: Player | None,
    is_first_round: bool,
    ):
```

game 只留最重要的參數
舉例來說這邊是回合要運作需要的資料，而 game 完全不需要知道這回合發生什麼事，只需要拿回 top_play, top_card, is_game_over 就能判斷遊戲進行與否

我臨時有一個突發奇想的想法是, 開一個 RoundResult 類別
Round 每回合會 output RoundResult
下一回合再從 RoundResult 拿來當 input 持續跌代更新, 一直到遊戲結束
但這個想法沒有設計依據, 先記錄下來, 有機會再嘗試

還有實作需求中若發現需求有些地方是不合理, 是非常合理的, 工作也是這樣
